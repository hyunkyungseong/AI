# 플랜: 거래명세서 미리보기 "조(그룹)" 분리 발급 + 통합 엑셀(다중 시트) 생성

> 상태: 계획 승인 완료(2026-07-29) — 착수 전. 다음 세션에서 이어서 시작.

## Context (왜 필요한가)

지금 거래명세서 미리보기(오른쪽 "고객사 청구 명세서" 표)는 전체가 하나로 묶여서 "확정"을 누르면 거래명세서 1건(번호 1개)·Excel 1개 파일(시트 1장)로만 만들어집니다. 그런데 실제로는 KB증권처럼 한 업무(예: 거래원장)의 청구 항목을 **여러 거래명세서로 나눠 발급**해야 하는 경우가 있고(사용자 확인: 예를 들어 전산출력비/봉입비는 1조, 제작비류는 2조로), 이 여러 거래명세서를 각각 별도 파일로 받는 게 아니라 **엑셀 1개 안에 시트를 나눠서(1조 시트, 2조 시트...)** 받아야 합니다. 그리고 이 통합 파일은 "발행완료" 화면에서도 나중에 언제든 다시 받을 수 있어야 합니다(사용자 확정).

## 사용자와 확정한 설계

1. **조(그룹) 지정 위치**: 행마다 그룹을 고르는 게 아니라, 오른쪽 표의 품명 칸을 클릭해 여는 **조건 편집창(`ConditionRuleModal.tsx`)에서 규칙을 등록할 때 "조(시트명)"을 함께 선택/입력**한다 — 조는 규칙 저장 단위(거래처+업무명당 재사용되는 `청구품목규칙`)에 속하는 값.
2. **조의 기본값은 "작업명"이지만 사용자가 바꿀 수 있어야 함(사용자 확정, 중요)** — 분리 발급은 **선택적**이라, "작업명별로 나눠야 하는 경우"와 "여러 작업명이 섞여도 그냥 하나로 만드는 경우"가 둘 다 있음. 그래서:
   - 규칙의 조건에 "작업명 == X" 단일 조건이 포함돼 있으면, 조 입력칸의 기본값을 자동으로 그 작업명(X)으로 채워준다(타이핑 안 해도 되는 흔한 경우 커버)
   - 그 값은 그대로 써도 되고, 사용자가 직접 다른 문자열로 바꿔도 된다(여러 작업명을 하나의 조로 합치고 싶을 때, 또는 시트에 더 보기 좋은 이름을 쓰고 싶을 때)
   - 조를 아예 지정하지 않으면(빈 값) 지금처럼 거래명세서 1건으로 동작(하위 호환) — 최종적으로 오른쪽 표에 등장한 **조 값의 종류 수만큼** 거래명세서가 각각 발급됨(조가 전부 같거나 비어 있으면 1건)
3. **재다운로드**: "발행완료" 화면에서 이미 발급된 거래명세서를 다시 다운로드할 때도, 그 거래명세서가 속한 묶음의 통합 엑셀(여러 시트)을 언제든 다시 받을 수 있어야 함(사용자 확정) — 어느 조의 거래명세서번호로 다운로드를 눌러도 같은 통합 파일을 받는다.

## 핵심 설계 결정 (구현 전 반드시 인지해야 할 것)

- **원본 의뢰서 목록은 모든 조가 공유한다.** 왼쪽 원본 품목은 선택한 의뢰서 전체를 (품목,작업명,단가) 단위로 집계한 것이라, 의뢰서 하나가 여러 조에 걸친 항목(예: 출력비는 1조, 제작비는 2조)에 동시에 기여할 수 있음 — "이 의뢰서는 1조 소속"처럼 의뢰서 단위로 조를 나눌 방법이 없음. 그래서 **분리돼 나온 모든 거래명세서(조)는 전부 같은 의뢰서번호_목록 전체를 `거래명세서_의뢰서`에 저장**한다(미발행 목록에서 제외되는 기준과 일치, 부분취소 시 서로 영향 없음은 아래 참고).
- **부분/전체취소는 조 단위(거래명세서번호 단위) 그대로** — 한 조를 취소해도 다른 조(같은 의뢰서를 공유)에는 영향 없음(기존 "거래명세서 단위 취소" 원칙 유지, 범위 밖).
- **엑셀 통합 시, 도장 이미지 외 부가 요소(작성자 메모용 셀 코멘트·요청내용 커버시트)는 통합본에서 제외**한다 — 커버시트(`sheet1`, "요청내용")·셀 코멘트(`comments1.xml`, "작업명 기재"라는 내부 메모)는 고객에게 보여줄 필요 없는 내부용이라 병합 로직을 단순하게 유지하기 위해 뺀다(도장 이미지만 각 시트에 그대로 유지).

## DB 스키마 변경

### `청구품목규칙`에 컬럼 추가 (`scripts/init_db_mariadb.py`)
```sql
ALTER TABLE 청구품목규칙 ADD COLUMN 조 VARCHAR(50) NULL AFTER 최종청구품명;
```
규칙을 저장할 때 조(시트명) 문자열을 함께 저장 — NULL이면 미지정(하위호환).

### `거래명세서`에 컬럼 추가
```sql
ALTER TABLE 거래명세서 ADD COLUMN 묶음번호 VARCHAR(30) NULL AFTER 편집여부;
ALTER TABLE 거래명세서 ADD COLUMN 시트명 VARCHAR(50) NULL AFTER 묶음번호;
```
- `묶음번호`: 같은 확정 요청에서 여러 조로 나뉘어 만들어진 거래명세서들이 공유하는 값 — **새 채번 체계를 따로 만들지 않고, 그 묶음의 첫 번째 거래명세서번호를 그대로 재사용**(단일 거래명세서면 NULL, 즉 지금과 동일)
- `시트명`: 통합 엑셀에서 이 거래명세서가 차지할 시트 이름(조 이름을 그대로 사용, 없으면 미사용)
- `scripts/init_db.py`(SQLite/Streamlit)에도 동일하게 `migrate_...` 함수에 반영 필요(이번 기능은 Next.js 전용이라 계산 로직 자체는 안 건드리지만, 스키마 동기화 관례상 SQLite에도 컬럼은 추가해둔다 — app.py 화면 반영은 이번 범위 아님)

- 신규 `combine_거래명세서_시트들(시트_목록)` — `시트_목록: [(엑셀바이트, 시트명), ...]` (이미 `write_거래명세서_excel()`로 완성된 단일시트 xlsx 여러 개)를 받아 **하나의 워크북에 시트를 이어붙인 xlsx bytes**를 반환:
  - 첫 번째 파일을 기본 컨테이너로 사용(styles.xml·theme·sharedStrings는 모든 파일이 같은 템플릿에서 나와 완전히 동일 — 스타일 인덱스 재넘버링 불필요)
  - `sheet1.xml`(요청내용 커버시트)·`comments1.xml`·`vmlDrawing1.vml`은 통합본에서 제거(위 설계 결정 참고)
  - 2번째 파일부터: 그 파일의 `sheet2.xml`(품목 채워진 실제 데이터) + `drawing1.xml`(도장 이미지 앵커, 위치는 항상 동일)을 각각 `worksheets/sheetN.xml`·`drawings/drawingN.xml`로 이름 바꿔 추가, 도장 이미지 자체(`media/image1.png`)는 모든 시트가 동일하므로 파일 하나만 공유
  - `[Content_Types].xml`에 새 시트/드로잉 Override 추가, `xl/_rels/workbook.xml.rels`에 새 worksheet relationship 추가, `xl/worksheets/_rels/sheetN.xml.rels`에 drawing relationship 추가(printerSettings는 첫 시트 것 공유 재사용), `workbook.xml`의 `<sheets>`에 `<sheet name="{시트명}" .../>` 추가 + `_xlnm.Print_Area` 정의된 이름을 시트별로 추가(각 파일이 이미 갖고 있던 자기 print area 값 그대로, `localSheetId`만 새 시트 인덱스로 교정)
  - 시트명은 Excel 규칙에 맞게 정리(31자 제한, `[]:*?/\` 등 금지문자 제거)
  - **참고(사전 조사 완료)**: 템플릿 내부 관계 확인 결과 `sheet2.xml.rels`가 `drawing1.xml`(rId3)·`printerSettings2.bin`(rId2)·`comments1.xml`(rId5)·`vmlDrawing1.vml`(rId4)을 참조하고, `drawing1.xml.rels`가 `media/image1.png`(rId1)를 참조하는 구조. `comments1.xml`은 B12 셀에 "'작업명' 기재"라는 내부 작성자 메모일 뿐이라 통합본에서 제외해도 무방.

### `scripts/api.py`
- **`POST /거래명세서요청` 확장**: `품목_최종`의 각 행에 `조`(Optional[str]) 필드 추가. 서버가 `조`별로 그룹핑해서:
  - 그룹이 1개(또는 전부 조 없음)면 **지금과 완전히 동일하게 거래명세서 1건** 생성(하위호환, 회귀 없음)
  - 그룹이 2개 이상이면 그룹별로 공급가액(그 그룹 금액 합)·세액(`billing.부가세_계산()`)·합계를 각각 계산해 **거래명세서를 그룹 수만큼 각각 채번·저장**, 전부 같은 `의뢰서번호_목록` 전체를 `거래명세서_의뢰서`에 저장, `묶음번호`는 첫 그룹의 거래명세서번호로 통일해서 전부 저장, `시트명`은 각자의 조 이름
  - 규칙 저장(`규칙` 필드)도 각 규칙에 실린 `조`를 그대로 `청구품목규칙.조`에 저장
- **`GET /거래명세서엑셀/{no}` 확장**: 조회한 거래명세서의 `묶음번호`가 있으면, 같은 `묶음번호`를 가진 형제 거래명세서 전부를 조회 → 각각 (기존 로직 그대로, 스냅샷 있으면 스냅샷/없으면 재계산) 단일시트 엑셀을 만든 뒤 `billing.combine_거래명세서_시트들()`로 합쳐서 반환. `묶음번호`가 없으면(기존 건 전부 해당) 지금처럼 단일 파일 그대로 반환 — **기존 발행 건은 전혀 영향 없음**
- **`POST /청구품목규칙 저장`(`_규칙_저장`)**: INSERT문에 `조` 컬럼 추가

3. 로컬 격리 환경(로컬 FastAPI+MariaDB, 사무실 PC 미접촉)에서 실제 흐름: 조 2개로 규칙 등록 → 확정 → 거래명세서 2건이 생성되고 같은 묶음번호를 공유하는지 DB로 확인 → 발행완료 화면에서 어느 조로 다운로드해도 시트 2개짜리 통합 파일이 오는지 확인
4. 회귀 확인 — 조를 전혀 안 쓰는(지금까지 하던 대로) 기존 흐름이 여전히 거래명세서 1건·단일시트 파일로 동일하게 동작하는지(기존 발행 건 재다운로드 포함)
5. `npx tsc --noEmit`·`npx eslint .`·`npm run build`

## 비개발자용 확인 체크리스트
1. 미리보기에서 품명 칸 클릭 → 조건 편집창에 "조(시트명)" 입력란이 보이는지 확인, "1조"라고 입력 후 저장
2. 다른 품명 칸에 "2조"로 규칙 하나 더 등록 → 오른쪽 표가 1조/2조로 나뉘어 보이고 각각 소계가 나오는지 확인
3. 확정 → 발행요청목록/발행완료에 거래명세서가 2건(번호 2개) 생성됐는지 확인
4. 둘 중 아무 거래명세서나 다운로드 → 엑셀 파일을 열었을 때 시트가 "1조"·"2조" 2개로 나뉘어 있고, 각 시트에 해당 품목·도장이 정상적으로 들어있는지 확인
5. 조를 전혀 안 쓰고(기존 방식대로) 확정한 경우, 지금까지와 동일하게 거래명세서 1건·단일 시트 파일로 나오는지 확인(회귀 없음)
