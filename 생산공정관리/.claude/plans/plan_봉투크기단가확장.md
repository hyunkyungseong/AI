# 플랜: 봉투 크기 구분(소·중·대) 확장 및 단가 반영

> 상태: ✅ [Phase 1] 완료 — 실시간 API가 `자재형태` 값을 자유 문자열로 받아 그대로 저장 (2026-07-19) → ⏳ [Phase 2] 미착수 — 단가 반영은 별도 트리거 발생 시 진행

## 배경

생산공정관리시스템 담당자 전달용 API 문서(`docs/API규격서_생산공정관리시스템전달용.md`)를 검토하던 중, 실시간 수신 API(`POST /운영통계자료수신`)가 `자재형태`(봉투 종류 구분) 값을 아예 받지 못하는 게 확인됐습니다(요청 스키마에 필드 자체가 없어 보내줘도 조용히 버려짐). 이를 계기로, 사용자가 지금의 "일반봉투/각대대봉투" 2종 구분을 넘어 **향후 소·중·대봉투처럼 더 세분화된 구분**을 하고 싶다는 방향을 확인했습니다.

두 단계로 나눠 진행합니다 — Phase 1(오늘)은 값을 받아서 저장만, Phase 2(향후)는 그 값으로 실제 단가를 다르게 매기는 것까지.

## [Phase 1] 값 수신·저장 — ✅ 완료 (2026-07-19)

- [x] `scripts/api.py`의 `자재행` 요청 스키마에 `자재명`·`자재형태` 선택 필드 추가 — 어떤 문자열이 오든 제한 없이 받음
- [x] `scripts/data_transform.py`의 `merge_자재()`가 이미 채워진 `자재형태` 값을 우선 존중하도록 보완 (① 요청에 `자재형태`가 있으면 그대로 사용 → ② 없고 `자재명`이 있으면 기존처럼 자동 분류 → ③ 둘 다 없으면 "일반봉투" 기본값 — 배치 경로는 동작 변화 없음)
- [x] `docs/API규격서.md`·`docs/API규격서_생산공정관리시스템전달용.md`·웹 아티팩트 갱신 — "저장은 되지만 소/중/대별 단가 반영은 아직 안 됨"을 명확히 표기(오해 방지)
- **의도적으로 하지 않은 것:** 단가마스터 스키마·`calc_공급가맵()`·거래명세서 Excel 생성·Next.js 단가관리 화면은 오늘 손대지 않음 — 즉 "소봉투" 같은 새 값이 들어와도 계산은 지금처럼 "각대대봉투가 아니면 일반 단가"로 처리됨

## [Phase 2] 단가 반영 — ⏳ 미착수

**착수 조건:** 생산공정관리시스템이 실제로 `자재형태`(또는 `자재명`) 값을 보내기 시작하고, 그 값에 "일반봉투"·"각대대봉투" 외의 값(예: 소봉투·중봉투·대봉투)이 포함되는 것이 DB에서 확인되면 착수합니다.

**그때 해야 할 일 (개요 — 상세 설계는 착수 시점에 별도로):**
- [ ] `단가마스터` 스키마 확장 검토 — 현재 `각대대봉투단가`·`각대대봉투봉입단가` 2개 필드만 있어 봉투 종류가 고정 2종 전제. 소/중/대처럼 종류가 늘어나면 ① 필드를 계속 추가하는 방식(예: `소봉투단가`·`중봉투단가`…) ② `자재형태`를 키로 쓰는 더 유연한 구조(예: 봉투 단가 전용 하위 테이블)로 재설계하는 방식 중 선택 필요
- [ ] `scripts/billing.py`의 `calc_공급가맵()`·`generate_거래명세서_excel()` — 지금은 "각대대봉투인지 아닌지"만 분기하는 로직을 실제 저장된 `자재형태` 값 기준으로 단가를 찾도록 수정
- [ ] Next.js "단가관리" 화면(`components/PricingMaster.tsx`·`PricingFormDialog.tsx`) — 봉투 종류별 단가 입력 필드를 스키마 변경에 맞게 갱신
- [ ] `docs/API규격서.md`·전달용 문서·웹 아티팩트도 그 시점에 다시 갱신(단가 반영이 실제로 되는 시점으로 문구 교체)

**Phase 1과의 연결:** Phase 1에서 `자재형태`를 자유 문자열로 그대로 저장해두었기 때문에, Phase 2 착수 시점엔 이미 DB에 실제 값이 쌓여 있어 그 분포(어떤 이름의 값들이 실제로 들어왔는지)를 보고 스키마를 설계할 수 있습니다.
