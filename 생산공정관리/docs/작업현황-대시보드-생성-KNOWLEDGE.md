## 📌 프로젝트 개요
- **프로젝트명:** 작업현황 대시보드 생성
- **업종:** DM(다이렉트메일) 및 교재 제작
- **목적:**
  1. 공정관리시스템 자료(`운영통계자료.xlsx`)를 활용해 통계 생성
  2. 거래처별 출력·봉입 작업 현황을 시각화
  3. 생산 작업에 대한 거래명세서 발행 관리
  4. 거래명세서 미발행 건 존재 여부 체크
  5. 웹 환경에서 대시보드를 팀 내부에서 볼 수 있게 함
- **주요 시각화 항목:**
  - 거래처별 작업 현황 (출력, 봉입)
  - 전월 대비 현황
  - 전년 동월 대비 현황
  - 담당자별 작업 현황
  - 거래명세서 발행 현황 및 미발행 건 알림
- **원본 데이터:** `data/운영통계자료.xlsx`
- **결과물 전달 대상:** 우리 팀 내부
- **팀 규모:** 2 ~ 5명
- **주 사용자 유형:** 비개발자 (코딩을 잘 모름)

## 🔄 핵심 업무 흐름

```
[운영통계자료.xlsx 업데이트]
         ↓
[데이터갱신_후_실행.bat 실행 → preprocess.py 자동 처리]
         ↓
[대시보드에서 작업 현황 확인]
         ↓
[마케팅 담당자: 미발행 목록에서 의뢰서 선택]
  → "거래명세서 요청" 버튼 클릭 (거래명세서번호 자동 채번)
         ↓
[거래명세서이력 DB에 발행대기(발행여부=0) 저장 → 미발행 목록에서 즉시 제거]
         ↓
[경영지원부 담당자: 발행요청목록(발행대기 건만 표시)에서 검색]
  → 의뢰서번호를 파이프(`|`) 구분으로 발행요청목록 상단 검색창에 입력 → "검색" 버튼 클릭
  → 합계(장수·봉입건수·출력페이지·청구페이지) 확인
         ↓
[이상 없으면 "거래명세서 발행" 버튼 클릭 → 발행완료(발행여부=1) 업데이트 → 발행완료 탭으로 이동]
         ↓
[거래명세서 Excel 생성 → 고객사에 이메일 발송 (미구현)]
```

- **미발행 건:** 거래명세서이력 DB에 등록되지 않은 업무의뢰서 (발행여부 관계없이 이력에 있으면 미발행 목록에서 제외)
- **발행여부 값:** `0` = 발행대기 (마케팅 요청됨, 발행요청목록 탭에 표시), `1` = 발행완료 (경영지원부 처리됨, 발행완료 탭에 표시)
- **담당자 역할 분리:** 마케팅 담당자(요청) ↔ 경영지원부 담당자(검토·발행)
- **의뢰서번호 검색 형식:** 발행요청목록/발행완료 탭 검색창은 파이프(`|`) 구분 한 줄 문자열로 입력 (미발행 목록에는 검색·복사 기능 없음, 2026-07-17 삭제)
- **발행요청목록 탭 (발행대기 전용):** "취소" 버튼(레벨1·레벨2)으로 의뢰서를 미발행 목록으로 되돌림 (복구 불가). 부분 취소 규칙은 아래 "부분 취소" 항목 참고
- **발행완료 탭 (신규):** "발행 취소" 버튼으로 발송여부만 0으로 되돌림 → 발행요청목록 탭에 발행대기 상태로 다시 나타남 (거래명세서이력 행은 유지)
- **필터 적용 범위:** 발행요청목록·발행완료 두 탭 모두 사이드바 전체 필터(사업부·기간·거래처·담당자·업무명) 적용 (`_render_발행_섹션()` 공통 함수, `scripts/app.py`)
- **거래명세서번호 채번 규칙 (2026-07-17 추가):** 형식 `D(또는N)-yyyymm-00001`
  - `D`=DM사업부, `N`=N사업부, `yyyymm`=요청 시점(오늘) 연월, 뒤 5자리는 사업부·연월별 순번
  - "거래명세서 요청" 클릭 시 `_발급_거래명세서번호()`(`scripts/app.py`)가 `거래명세서번호_카운터` 테이블(사업부·연월별 마지막순번)에서 자동 발급
  - **취소해도 번호는 재사용하지 않음** (카운터는 증가만 함 → 결번 허용, 회계 추적용)

  1. **레벨1 (요약, 항상 표시)** — 거래명세서번호+업무명 기준 합산 (건수·합계만). "거래명세서 발행" 버튼(발행대기 탭)·"발행 취소"(되돌리기, 발행완료 탭)는 여기서 체크한 그룹 전체 단위로 동작. **"취소"**(발행대기 탭)는 체크한 그룹에 속한 의뢰서를 일괄 취소
  2. **레벨2 (목록, 레벨1 체크 시 표시)** — 체크한 그룹에 속한 의뢰서번호별 행. 발행완료 탭에서는 조회(레벨3 표시) 전용이지만, **발행대기 탭에서는 "취소" 버튼이 있어 개별 의뢰서번호만 선택 취소 가능**

### 거래명세서이력 MariaDB 정규화 설계 (2026-07-19 확정)
> 기존 SQLite `거래명세서이력` 1개 테이블(업무의뢰서번호목록을 JSON-in-TEXT로 저장)을 아래 2개 테이블로 분리. `품목`은 실제 라인아이템(수량·단가)이 아니라 업무명 요약 텍스트이고, 공급가액·세액·합계는 항상 거래명세서(그룹) 단위 합계로 계산·저장되던 값이라 — 개별 의뢰서 단위 금액 배분은 새로 만들지 않고, 집계값은 그룹 테이블에 그대로 두고 "의뢰서번호 목록"만 정규화함.

### 운영통계자료 데이터 반영 방식 (2026-07-19)
- `scripts/preprocess.py`에 `save_to_mariadb()` 함수 추가 — `processed.pkl` 저장은 그대로 유지하면서 **추가로** MariaDB `운영통계자료` 테이블에 TRUNCATE & INSERT 방식으로 반영

- MariaDB 반영 실패 시(서버 미기동 등) 경고만 출력하고 pkl 저장은 그대로 성공 처리 — 기존 대시보드 동작에는 영향 없음

### 당사 생산공정관리시스템 연동 — 실시간 API 수신 (2026-07-19 신규)
> 기존 엑셀 배치 방식(`data/운영통계자료.xlsx` 수동 업로드) 외에, 당사 생산공정관리시스템이 업무의뢰서 완료 시 실시간으로 데이터를 보내주는 방식을 추가함. **두 방식은 당분간 병행**(이중화·백업용) — 어느 한쪽만 남기는 결정은 아직 안 됨

| 항목 | 결정 내용 |
|---|---|
| 연동 방향 | **Push** — 생산공정관리시스템이 우리 FastAPI(`scripts/api.py`)를 호출 |
| 전송 단위 | **건별 실시간** — 업무의뢰서 하나 완료 시, 그 의뢰서에 속한 모든 작업내역 행 + 관련 자재사용량을 한 번의 호출로 전송 |
| 필드 구성 | 현재 `운영통계자료.xlsx`와 동일한 컬럼 |
| 재전송 처리 | 같은 업무의뢰서번호로 다시 오면 기존 데이터를 `DELETE` 후 `INSERT`로 통째로 교체 (수정·정정 재전송 안전) |
| API 규격서 | `docs/API규격서.md` — 당사 시스템 개발 담당자 전달용 |

**왜 "건별 실시간"인데 그룹 계산(확정청구페이지)이 문제없이 되는가:** `apply_billing_logic()`은 (업무의뢰서번호+작업명) 그룹 전체를 봐야 계산되는데, 한 업무의뢰서번호의 모든 행이 항상 한 번의 호출에 다 같이 오기 때문에 그 안에서는 그룹이 항상 완결된 상태 — 배치 처리와 동일한 방식으로 계산 가능. (만약 한 의뢰서의 행이 여러 번에 걸쳐 나눠 온다면 이 전제가 깨지므로, API 규격서에 "같은 의뢰서 행은 반드시 한 번에 전부" 라고 명시해둠)

**아키텍처 — 로직 공유:**
```
scripts/data_transform.py   ← 가공 로직 단일 소스 (반제품 처리·거래처명 파싱·사업부 구분·자재 조인·청구페이지 계산)
        ↑ import                              ↑ import
scripts/preprocess.py                  scripts/api.py
(엑셀 배치, TRUNCATE&INSERT)      (실시간 1건, DELETE&INSERT 스코프 제한)
```
- 로직을 두 파일에 각각 복사해두면 한쪽만 고치고 다른 쪽을 놓치는 버그가 생기기 쉬워서 공용 모듈로 분리함
- **발견된 버그:** 자재종류 일부만 있는 작은 배치(예: 봉투·용지만 있고 삽지·미구분 없음)에서는 pivot이 해당 자재종류 컬럼만 만들어서 `봉투_사용량` 등 누락 컬럼에서 `KeyError` 발생 — 전체 배치(36,804행)에는 4종류가 항상 다 나와서 발견 못 했던 잠재 버그. `merge_자재()`가 4종 컬럼(봉투·용지·삽지·미구분)을 항상 보장하도록 수정

### 핵심 계산 로직 (출력 vs 봉입)

> **출력과 봉입은 별도 행이 아니라 같은 행에 함께 기록됩니다.**

| 지표 | 사용 컬럼 | 설명 |
|---|---|---|
| 출력량 (장비 기준) | `출력페이지` (장비출력페이지) | 장비가 처리한 페이지 수. 양면 뒷면 미인쇄도 포함 |
| 출력량 (실제 기준) | `청구페이지` (실제출력페이지) | 실제 인쇄된 페이지만 집계 |
| 종이 소비량 | `장수` (출력용지 장수) | 사용된 종이 장 수 |
| 봉입량 | `건수` (봉입건수) | 봉투에 넣은 건 수 |

**과금(거래명세서) 기준:**
- 거래처별로 다름: `출력페이지` 기준 또는 `청구페이지` 기준
- 카드사 등 대형 거래처는 `청구페이지`(실제출력페이지) 기준으로 거래명세서 발행

**업무의뢰서번호 단위 청구 계산 규칙:**
```
[경우 1] 첫 행만 청구페이지 > 0, 나머지 행은 모두 0
  Row 1: 청구페이지 = 500  ← 전체 합계가 이미 첫 행에 표기됨
  Row 2: 청구페이지 = 0
  Row 3: 청구페이지 = 0
  → 청구 = 500 (첫 행 값 그대로 사용)

[경우 2] 2번째 이후 행 중 청구페이지 > 0 인 행이 하나라도 존재
  Row 1: 청구페이지 = 200
  Row 2: 청구페이지 = 150
  Row 3: 청구페이지 = 0
  → 청구 = 200 + 150 + 0 = 350 (첫 행부터 마지막 행까지 합산)

[경우 3] 그룹 내 모든 행의 청구페이지 = 0
  Row 1: 청구페이지 = 0, 출력페이지 = 200
  Row 2: 청구페이지 = 0, 출력페이지 = 100
  → 청구 = 200 + 100 = 300 (전체 행의 출력페이지 합산)
```

## 🔑 주요 결정사항

- **반제품 처리 (2026-06-07 확정):** 반제품여부=Y인 행은 봉입 작업이 없으므로 해당 행의 건수를 0으로 처리. preprocess.py `apply_반제품_logic()`에서 청구페이지 계산 전에 자동 적용.
- **출력/봉입 집계 방법:** 출력과 봉입은 같은 행에 함께 기록됨. `건수`=봉입건수, `출력페이지`=장비출력페이지, `청구페이지`=실제출력페이지로 각각 집계
- **청구 단위:** `업무의뢰서번호` 기준으로 청구페이지를 계산. 단, 거래명세서 발행 시 여러 업무의뢰서번호를 합쳐서 1장으로 발행하는 경우도 있음
- **청구페이지 계산 규칙 (업무의뢰서번호 그룹 기준):**
  - 경우 1 — 첫 행만 청구페이지 > 0, 나머지 모두 0 : 첫 행의 청구페이지 그대로 사용 (전체 합계가 이미 표기된 것)
  - 경우 2 — 2번째 이후 행 중 청구페이지 > 0 존재 : 첫 행부터 마지막 행까지 청구페이지 합산
  - 경우 3 — 그룹 내 모든 행 청구페이지 = 0 : 전체 행의 출력페이지 합산으로 청구
- **과금 기준:** 거래처별로 다름. 카드사 등 대형사는 `청구페이지` 기준으로 거래명세서 발행
- **공급가액 계산 공식 (2026-07-24 정정 — 추가봉입비에서 삽지 분리):**
  ```
  봉입건수      = 업무의뢰서번호 그룹 내 전체 건수 합계
  추가용지      = 장수_합 - 봉입건수_합  (장수 또는 봉입건수가 0이면 0)
  출력료        = 확정청구페이지 × 출력단가
  봉입료        = 봉입건수 합계  × 봉입단가
  추가봉입비    = 추가용지 × 추가봉입단가             (2026-07-24까지: 삽지 포함이었음 — 아래 참고)
  동봉물삽입비  = 삽지_사용량_합 × 동봉물삽입단가      (2026-07-24 신규 항목 — 단가마스터에 필드 추가)
  용지제작비    = 용지_사용량_합 × 용지제작단가
  봉투제작비    = 봉투_사용량_합 × 봉투제작단가
  삽지제작비    = 삽지_사용량_합 × 삽지제작단가
  공급가액      = 출력료 + 봉입료 + 추가봉입비 + 동봉물삽입비 + 용지제작비 + 봉투제작비 + 삽지제작비
  세액          = 공급가액 × 10%
  합계          = 공급가액 + 세액
  ```
  - **추가봉입비/동봉물삽입비 분리(2026-07-24):** 원래 `추가봉입비 = (삽지_사용량_합 + 추가용지) × 추가봉입단가`로 삽지와 추가용지를 한 항목에 합쳐 청구하고 있었음(버그 아닌 기존 확정 공식) — 사용자가 실사용 중 "추가봉입비는 순수하게 추가로 들어간 용지만 의미해야 하고, 삽지는 별도 '동봉물삽입비'로 청구돼야 한다"고 확정해 분리함. 신규 `동봉물삽입단가` 필드는 마이그레이션 시 기존 거래처마다 `추가봉입단가`와 동일한 값으로 백필돼, 변경 직후 총 청구액은 그대로 유지됨(`scripts/init_db_mariadb.py`의 `migrate()`). 상세: `docs/CHANGELOG.md` 2026-07-24 항목

  - 단가 필드가 DB에서 null인 경우 0으로 처리 (NaN 연산 버그 방지)

  - (업무의뢰서번호, 작업명) 단위로 단가 각각 적용 후 합산 (2026-06-21 완료)
