# 우편요금 관리 — 미발행 목록 입력 + 거래명세서 미리보기 자동 반영

> 상태: ✅ 완료(로컬 코드·검증 2026-08-22, 사무실 PC 배포 2026-08-23 — 파일 복사·마이그레이션
> (`업무의뢰서_우편요금` 테이블 생성)·FastAPI 재시작까지 사용자 확인). 로컬·사무실 PC 완전
> 동기화 상태, 남은 미배포 항목 없음.

## Context — 왜 이 작업을 하는가

마케팅 담당자가 우체국으로 발송하는 업무는 우편요금이 발생하는데, 지금은 이걸 시스템 밖에서 수기로
관리하고 있다. 월 1회 발송하는 업무는 기존 "새 행 추가"(거래명세서 미리보기 오른쪽 표에서 수동으로
품명·수량·단가를 직접 타이핑하는 기능, 2026-08-12 도입)로 그때그때 입력해서 해결이 되는데, **매일
발송하는 업무는 영업일 수만큼 매번 수기로 우편요금을 관리해야 해서** 이 방식으로는 감당이 안 된다.

요청하신 방식: **미발행 목록 화면에서 업무의뢰서(의뢰서 단위) 하나하나에 우편요금을 입력해두면**,
나중에 그 의뢰서들을 묶어서 "거래명세서 요청"을 누를 때 **미리보기 왼쪽 "원본" 표에 자동으로
반영**되게 한다 — 매번 미리보기에서 다시 입력할 필요가 없어짐. 우편요금은 수량·단가 개념이 필요
없고 **금액만** 있으면 된다.

## 코드에서 확인한 사실 (Read-only 조사 완료)

- **미발행 목록**(`GET /미발행목록`, `scripts/api.py:551`)은 `운영통계자료`를 매번 계산해서 만드는
  화면이라, 사용자가 입력한 값을 저장할 곳이 없다. `운영통계자료` 테이블 자체는 생산공정관리시스템이
  실시간으로 밀어넣고(`POST /운영통계자료수신`) `preprocess.py`가 통째로 재적재(TRUNCATE)도 하는
  테이블이라 **여기에 우편요금을 저장하면 안 됨** — 별도 테이블이 필요하다
- 화면은 `frontend/components/InvoiceSelectionTable.tsx` — 수천 행을 가상 스크롤(`useVirtualRows`)
  + `React.memo`로 그리는 구조(SKILL-26). 체크박스처럼 "그 행 하나만" 리렌더되게 설계돼 있어, 우편요금
  입력칸도 같은 방식(행별 값 하나만 prop으로, 부모 콜백은 useCallback으로 고정)으로 추가해야 함
- 거래명세서 미리보기(왼쪽 "원본" 표)는 `billing.build_품목행()`이 만드는데, 의뢰서 여러 개를
  **작업명 단위로 묶어서** `_작업별_품목누적()`을 호출하는 구조(2026-08-20 리팩터링, SKILL 참고).
  우편요금은 특정 작업명에 속하는 게 아니라 **의뢰서 단위 정액 비용**이라, 작업명별 루프 안에 넣으면
  의뢰서가 여러 작업명에 걸쳐 있을 때 중복 계산될 위험이 있음 — **루프 밖에서 한 번, 선택된 의뢰서
  전체의 우편요금 합계로 별도 항목 추가**하는 게 안전
- `calc_공급가맵()`(미발행 목록 "예상공급가액" 계산)에도 같이 반영해야 "예상 금액"과 실제 확정 금액이
  어긋나지 않음(2026-08-20에 이미 한 번 이 두 함수가 따로 놀아서 버그 났던 전례— `bug_공급가액계산_불일치.md`)
- 원본 품목 타입(`frontend/lib/billingRules.ts`의 `원본품목`, `billing.정렬행_원본목록()`)은 지금
  `단가: number`가 **필수(nullable 아님)** — 조건식 평가(`평가_조건()`)에서 단가 비교도 함. 타입을
  건드리는 대신 **수량=1, 단가=금액**으로 넣으면(금액=수량×단가 그대로 유지) 기존 코드 전혀 안 건드리고
  자연스럽게 흘러감 — 화면엔 "수량 1 / 단가 X원 / 금액 X원"으로 보임(약간 어색하지만 기능은 완전함)
- 거래명세서 Excel 코드표(P/M/MM/SI/E/F/H/BB/AB/D)는 전부 이미 용도가 정해져 있음(D=디자인비도
  예약돼 있음, 지금 안 쓰여도 자리 있음) — **우편요금에 쓸 빈 코드가 없다**, 사용자 확인 필요

## 확정된 설계 (AskUserQuestion으로 사용자 확인 완료, 2026-08-22)

- **표시 단위**: 하나로 합산하지 않고, **거래처+업무명 단위로 합산**해서 업무명 개수만큼 줄이 생김
  (예: 한 거래처에 업무명이 2개 섞여 있으면 우편요금도 2줄) — 기존 `_g = groupby(["작업명","거래처명","업무명"])`
  보다 한 단계 넓은 "업무명" 단위 그룹핑이 신규로 필요함(작업명 단위 아님)
- **Excel 코드(구분 열)**: **"PO"**로 표시(사용자 확정, 2026-08-22 — 처음엔 "코드 없이 품목명만"으로
  검토했으나 "PO"로 변경). 기존 템플릿 하단 범례(P/M/MM/SI/E/F/H/BB/AB/D)엔 없는 새 글자지만, 구분 열은
  코드맵이 주는 문자열을 그대로 찍는 자유 텍스트 셀이라 템플릿 자체 수정은 불필요

## 구현 파일과 변경 지점

### 1. DB 스키마 — `scripts/init_db_mariadb.py`
신규 테이블 `업무의뢰서_우편요금`:
```sql
CREATE TABLE IF NOT EXISTS 업무의뢰서_우편요금 (
    업무의뢰서번호  VARCHAR(20) PRIMARY KEY,
    금액            DECIMAL(10,2) NOT NULL DEFAULT 0,
    등록일          DATE DEFAULT (CURRENT_DATE),
    수정일          DATE DEFAULT (CURRENT_DATE)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```
`운영통계자료`(실시간 수신+주기적 TRUNCATE 재적재 대상)와 분리된 별도 테이블이라 재적재해도
우편요금 입력값이 안전하다. 의뢰서가 취소돼 미발행 목록으로 돌아와도 값은 남아있음(삭제 안 함,
거래명세서품명이력과 동일한 관례).

## 참고 — 확정 시 "미분류 확정 경고"와의 관계

"우편요금"도 다른 품목과 마찬가지로 청구품목규칙(조건식)에 매칭 안 되면 왼쪽 원본에는 보이되 오른쪽
최종 표로 안 넘어가 미분류로 분류된다(2026-08-17 이후 기존 동작) — 즉 처음 한 번은 그 거래처+업무명에
"우편요금" 조건식(예: 품목 == 우편요금)을 만들어둬야 확정 시 경고 없이 자동으로 넘어간다. 다른 신규
품목(공정별단가청구 9종 등)이 추가됐을 때와 동일한 기존 동작이라 별도 처리 안 함.
