# 버그 수정: 봉입비(M)가 "자재단가 등록된 봉투"에서 수작업 물량까지 중복 청구

> 상태: ✅ 코드 수정·검증 완료(2026-08-23, 로컬 PC만) — **사무실 PC 배포는 다음 승인 시 진행 예정**.
> 실제 수정: `scripts/billing.py` 348행, `_자재별_처리()` → `_자재비례배분_처리()`로 함수명 1줄 교체
> (아래 "수정 방향"과 동일). 검증 결과는 파일 맨 아래 "검증 결과" 섹션 참고.

## Context (왜 필요한가)

사용자가 의뢰서 97509(현대해상 자동차증권) 거래명세서 미리보기 화면을 보다가 "자재추가로 나온
'중봉투봉입' 수량에 수작업 수량이 중복된 것 같다"고 제보. 조사 결과 실제 금액에 영향을 주는
버그로 확인됨.

## 코드에서 확인한 사실 (Read-only 조사 완료)

- 97509의 실제 DB 값(운영통계자료, 작업명="자동차증권" 부분): `봉입`(기계) 합계 4,128건,
  `수작업` 합계 1,339건. 화면에 뜬 "수작업비(자동차증권)" 수량(1,339)은 이 DB 값과 정확히
  일치함 — 수작업 건수 자체는 문제 없음.
- 봉투 자재 실사용량(자재사용현황, 작업명="자동차증권"): 중봉투(자재코드97) 2,671 + 소봉투(자재코드98)
  2,796 = 5,467 — 이는 **기계+수작업을 합친 전체 물량**과 정확히 같음(4,128+1,339=5,467).
  즉 자재사용현황은 삽입 방식과 무관하게 "실제로 쓴 봉투 개수"만 기록하는 구조.
- 설계 의도(`scripts/billing.py` 338~342행 주석, 2026-08-21): 봉입비(M, 공임)는 "기계로 넣은
  물량만" 청구하고 수작업 물량은 별도 "수작업비(H)"로 분리 청구해야 이중 계산을 피할 수 있다고
  **이미 인지하고 있었음** — 그래서 344~347행에서 `배송계열합 > 0`(신규 데이터)이면
  `봉입_기준수량 = 봉입`(기계 전용 4,128)으로 제한하도록 짜여 있음.
- **그런데 이 제한이 실제로는 지켜지지 않음**: 348행이 호출하는 `_자재별_처리()`(153행)는
  `자재별dict`(봉투자재별, 실제 봉투 사용량 원본 — 이번 사례는 5,467)에 그 자재의 **등록된
  자재단가(단가마스터_자재단가)가 있으면**, `총수량`(여기선 봉입_기준수량=4,128) 파라미터를
  무시하고 **그 자재의 실사용량 원본을 그대로** 청구수량으로 씀(153~183행 — `잔여 = 총수량`에서
  매칭된 자재의 원본 수량을 그냥 빼기만 할 뿐, 각 자재 줄 자체는 원본 수량 그대로 청구됨). 자재에
  등록가격이 없을 때만 "총수량-매칭분=잔여"가 기본단가 몫으로 정상적으로 캡핑됨.
  - 이번 사례처럼 봉투 자재 2종 모두에 자재단가가 등록돼 있으면 잔여 계산 자체가
    `4,128 - 2,671 - 2,796 = -1,339`(음수)가 나와, "기본단가 몫"은 0으로 사라지지만
    **자재별 줄(중봉투봉입 2,671·기계봉입 2,796)은 그대로 5,467건 청구**됨.
- **결과**: 화면에 보이는 실제 청구 항목
  - M 봉입비 "중봉투봉입" 2,671건 × 18원 = 48,078원
  - M 봉입비 "기계봉입" 2,796건 × 8원 = 22,368원
  - H 수작업비(자동차증권) 1,339건 × 50원 = 66,950원

  수작업으로 처리된 1,339건이 봉입비(M, 자재별 원본 수량에 포함)와 수작업비(H)에 **양쪽 다** 잡혀
  있음. (다이렉트 작업명도 봉입 관련 자재단가가 없어 이번 사례에선 봉입비 자체가 안 걸리지만,
  같은 자재에 등록가격이 있는 다른 거래처는 동일하게 영향받음 — 아래 "영향 범위" 참고)

- **영향 범위(현재 DB 기준)**: `단가마스터_자재단가.코드='봉입비'`로 등록된 행은 딱 4건뿐임
  - 현대해상 · 자동차증권(Daily, 다이렉트 포함) · 중봉투봉입/기계봉입 (이번 사례)
  - 현대해상 · 만기안내/만기예고(8회/월) · 만기 봉입
  - 삼성화재해상보험(주) · 계약보전(PLK)웰컴팩 · 웰컴팩 봉입비
  → 이 3개 거래처+업무명 조합이면서, 동시에 그 의뢰서가 신규 공정 데이터(배송계열합>0, 5월분
  이후)를 가진 경우에만 실제로 이중 청구가 발생함. 나머지 거래처·업무명은 봉입비에 자재단가
  자체가 없어 영향 없음(기존처럼 봉투합 전체를 그대로 청구 — 이 부분은 정상, 아래 "왜 봉입자재비(E)는
  괜찮은가" 참고).

## 왜 다른 품목(봉입자재비 E 등)은 문제없나

- **봉입자재비(E, 자재비)**: `_자재별_처리(... 봉투자재별, 봉입_기준수량이 아니라 봉투합(전체) ...)`
  로 호출됨(378행) — 여기는 "실제 쓴 봉투 개수만큼 재료비를 낸다"는 개념이라 기계·수작업 구분 없이
  전체(5,467)를 쓰는 게 원래부터 맞는 설계. 문제없음.
- **출력비(P)·출력자재비(F)**: `총수량`으로 넘기는 값(청구페이지, 또는 용지 실사용량)이 항상
  자재별dict 합계와 같거나(구버전) 별도의 비례배분 함수(`_자재비례배분_처리`)를 씀 — 이번
  버그와 같은 "총수량 < 자재dict합" 미스매치가 구조적으로 생기지 않음.
- **봉입비(M)만** "총수량(기계 전용, 신규 데이터)"과 "자재dict 원본 합계(기계+수작업 전체)"가
  서로 다를 수 있는 유일한 품목 — 그래서 이 함수(`_자재별_처리`)와 궁합이 안 맞음.

## 수정 방향 (제안)

`_자재별_처리()` 대신, 이미 있는 `_자재비례배분_처리()`(191행)를 봉입비(M) 계산에 쓰도록
바꾼다 — 딱 한 줄 교체(348행).

```python
# 변경 전
_자재별_처리(행데이터, "봉입비", 작업, rates, 봉투자재별 if 봉투합 > 0 else {}, 봉입_기준수량, rates.get("봉입단가", 0), 미등록수집)

# 변경 후
_자재비례배분_처리(행데이터, "봉입비", 작업, rates, 봉투자재별 if 봉투합 > 0 else {}, 봉입_기준수량, rates.get("봉입단가", 0), 미등록수집)
```

**왜 이게 맞는 수정인가:**
- `_자재비례배분_처리()`는 "총량은 그대로 보존하고, 그 총량을 자재별 실사용 비중으로만 나눈다"는
  함수(191~231행, 이미 출력비(P)에서 검증된 패턴). 봉입비에 적용하면:
  `배정량 = 봉입_기준수량 × (그 자재 실사용량 / 자재 전체 실사용량)`
  → 이번 사례라면 4,128 × (2,671/5,467) ≈ 2,018건(중봉투), 4,128 × (2,796/5,467) ≈ 2,110건(소봉투),
  합계 정확히 4,128건 — 수작업 물량 1,339건이 더 이상 봉입비에 안 잡힘.
- **구버전 데이터·자재단가 미등록 거래처는 100% 회귀 없음**: `_자재비례배분_처리()`는
  "총량 == 자재dict 합계"일 때 `배정량 = 총량×(사용량/총사용량) = 사용량`이 되어 `_자재별_처리()`와
  수학적으로 완전히 동일한 결과를 냄. 봉입비의 기존 호출(배송계열합=0, `봉입_기준수량 = 봉투합`)은
  항상 이 조건(총량=자재dict합)을 만족하므로 결과가 지금과 똑같음.
- **미등록수집(단가미등록 감지) 리포팅 방식이 약간 달라짐**: `_자재별_처리()`는 등록 안 된 자재마다
  개별로 미등록 항목을 남기는데, `_자재비례배분_처리()`는 등록 안 된 자재들을 합쳐서 한 줄로
  남김(둘 다 총 수량은 동일, 그룹핑 단위만 다름) — 실사용에 거의 영향 없는 사소한 차이지만
  구현 시 함께 안내드림.

## 후속 수정 — 비율배분 소수점 수량 보정 ✅ 완료 (2026-08-23, 같은 날)

사용자가 수정된 화면을 확인하다 "봉입비 수량이 2,016.808건처럼 터무니없는 숫자로 나온다"고 재차
제보. `_자재비례배분_처리()`가 비율(`총량 × 사용량/총자재량`)로 나누다 보니 자재가 여러 종류면
자연스럽게 소수점이 남는데, "건수"는 정수여야 의미가 통함(기존 `_자재별_처리()`는 항상 실사용량
그대로라 정수였어서 이번에 처음 드러남).

**수정**: `_자재비례배분_처리()`에 선택 인자 `정수반올림=False`(기본값, 기존 출력비 호출은 영향
없음) 추가 — True면 최대잔여법(largest remainder)으로 "총량(반올림)은 정확히 보존, 각 줄만
정수"가 되도록 배분한다. 봉입비 호출부에만 `정수반올림=True`를 넘김.

      1건씩 대조 — **318건 전부 정확히 일치(오차 0), 전부 정수** 확인. 표본이 아닌 전수 검증이라
      아직 나타나지 않은 극단적 데이터 패턴(예: 자재 개수가 유난히 많거나 총량이 0에 가까운 경우)도
      실제로 이미 이 population 안에 섞여 있었다면 걸러졌을 것
