# 생산공정관리 대시보드 — API 규격서

> 당사 생산공정관리시스템 개발 담당자에게 전달할 연동 문서입니다.
> 서버 코드: `scripts/api.py` (FastAPI) | 실행: `python scripts/api.py` (포트 8000)
> 이 문서는 API가 추가될 때마다 함께 갱신합니다. (최종 갱신: 2026-08-08)

---

## 1. 연동 방식 개요

- **방향: Push** — 당사 생산공정관리시스템이 업무의뢰서 처리를 완료할 때마다, 이 서버의 API를 호출해서 데이터를 보내주는 방식입니다. (우리 쪽이 주기적으로 가지러 가는 방식이 아닙니다)
- **전송 단위: 업무의뢰서(건) 단위, 실시간** — 업무의뢰서 하나가 완료되면, 그 의뢰서에 속한 **모든 작업내역 행을 한 번에** 호출 1건으로 보내주셔야 합니다. (한 의뢰서의 행을 여러 번 나눠 보내면 금액 계산이 틀어집니다 — 3번 항목 참고)
- **현재 서버 주소:** `http://192.168.30.201:8001` (2026-07-20 사무실 PC 이관 완료 — 사내망(LAN) 내부에서만 접속 가능. 포트가 8000이 아니라 **8001**인 이유: 이 사무실 PC에 이미 떠 있던 다른 서비스가 8000번을 쓰고 있어 우회. 생산공정관리시스템이 이 사무실 PC와 같은 사내망에 있지 않다면 별도 라우팅/VPN 확인 필요)
- **인증 (2026-07-19 확정):** `/운영통계자료수신`은 **`X-API-Key` 헤더**(고정 키, `db_config.py`의 `API_KEY` 값)로 인증합니다. 사람이 로그인하는 방식(2번 참고)과는 별개입니다 — 시스템 간 연동이라 계정이 필요 없습니다.

## 2-1. 로그인 인증 (화면용 API 전체 공통, 2026-07-19 추가)

> `/health`, `/운영통계자료수신`을 제외한 모든 API는 로그인 토큰이 필요합니다. 계정은 담당자별 개별 계정이며, 관리자가 `python scripts/create_user.py`로 생성합니다 (아직 화면 UI 없음).

### `POST /login`

**요청**
```json
{"사용자명": "gsyoon", "비밀번호": "********"}
```

**응답 (200)**
```json
{"access_token": "eyJhbGciOi...", "token_type": "bearer", "이름": "강서윤"}
```

**응답 (401)** — 사용자명 또는 비밀번호가 틀린 경우
```json
{"detail": "사용자명 또는 비밀번호가 올바르지 않습니다"}
```

### 이후 모든 요청에 토큰 첨부

```
Authorization: Bearer eyJhbGciOi...
```

- 토큰 유효시간: 12시간 (만료되면 다시 `/login` 호출)
- 토큰 없이/잘못된 토큰으로 호출 시 401 반환

## 3. `GET /summary`

`운영통계자료` 테이블을 (사업부 조건만 선택적으로 걸어서) 원본 그대로 반환합니다.

> **설계 방식(A안):** 탭1·2·3의 전월대비·거래처별/담당자별 집계 로직은 이 API로 옮기지 않고, 지금처럼 `app.py`(pandas)가 그대로 담당합니다. 이 API는 "데이터를 어디서 가져오는지"만 pkl 파일 → API 호출로 바꿔주는 역할입니다. 집계 로직을 그대로 재사용해 위험을 최소화하기 위한 선택입니다.

### 요청

| 파라미터 | 위치 | 필수 | 설명 |
|---|---|---|---|
| 사업부 | 쿼리스트링 | 선택 | `DM사업부` / `N사업부` 중 하나 이상. 생략하면 전체 반환. 예: `/summary?사업부=DM사업부&사업부=N사업부` |

### 응답 (200)

`운영통계자료` 테이블의 각 행을 JSON 객체로 담은 배열. 컬럼 구성은 KNOWLEDGE.md "운영통계자료 MariaDB 테이블 스키마" 참고 (`id` 포함, app.py 쪽에서는 사용하지 않아도 무방).

```json
[
  {"id": 1, "마케팅담당자": "강서윤", "등록자": "강서윤명", "업무명": "정기청구서",
   "업무의뢰서번호": "93690", "작업일자": "2026-03-02T22:05:08", ...},
  ...
]
```

### 성능 참고 (2026-07-19 측정)
- 전체(36,804행) 응답: 약 2초, 약 27MB
- 사업부 필터 적용 시(예: DM사업부 24,679행) 데이터량에 비례해 축소
- 사내망 내부 도구 기준으로는 허용 가능한 수준이나, 나중에 체감 속도 문제가 생기면 기간(날짜 범위) 필터 파라미터 추가를 검토

## 4. `POST /운영통계자료수신`

업무의뢰서 하나에 속한 작업내역·자재사용량 데이터를 수신합니다.

### ⚠️ 반드시 지켜야 할 것
- **같은 업무의뢰서번호에 속한 행은 반드시 한 번의 호출에 전부 포함**해서 보내주세요. 일부만 보내고 나중에 나머지를 따로 보내면, 청구페이지 합산 금액이 잘못 계산됩니다.
- **같은 업무의뢰서번호로 다시 호출하면, 기존에 저장된 그 의뢰서의 데이터는 전부 지워지고 새로 보낸 내용으로 완전히 교체**됩니다. (수정·정정 시 안전하게 재전송 가능)
- **인증 필수 (2026-07-19 추가):** 요청 헤더에 `X-API-Key: <전달받은 키 값>`을 반드시 포함해야 합니다. 키가 없거나 틀리면 401 오류가 반환됩니다. (로그인 방식이 아닙니다 — 2-1번 항목과 다름)

### 요청 (Request Body, JSON)

```json
{
  "업무의뢰서번호": "93690",
  "운영통계": [
    {
      "마케팅담당자": "강서윤",
      "등록자": "강서윤",
      "업무명": "정기청구서",
      "작업일자": "2026-07-19 10:00:00",
      "작업내역서번호": 12345,
      "작업내역서": "거래처명 - 업무상세내용",
      "작업명": "개인일반",
      "작업내역서상세": "상세 설명 (선택)",
      "반제품여부": "N",
      "P수": "1P",
      "장수": 100,
      "건수": 50,
      "출력페이지": 100,
      "청구페이지": 100
    }
  ],
  "자재사용현황": [
    {
      "작업내역서번호": 12345,
      "작업일자": "2026-07-19",
      "자재종류": "봉투",
      "작업명": "개인일반",
      "자재명": "일반봉투 100매",
      "자재형태": "일반봉투",
      "사용량": 50
    }
  ]
}
```
> 예시에는 `자재명`·`자재형태`를 둘 다 넣었지만 실제로는 어느 한쪽만 보내셔도 됩니다(`자재형태`가 있으면 그 값이 우선 사용되고, `자재명`만 있으면 자동으로 분류합니다 — 아래 필드 설명·지원 안내 참고).

### 필드 설명

| 필드 | 위치 | 타입 | 필수 | 설명 |
|---|---|---|---|---|
| 업무의뢰서번호 | 최상위 | 문자열 | 필수 | 이 요청 전체가 속한 업무의뢰서번호 (숫자처럼 보여도 문자열로 보내주세요) |

| 자재사용현황 | 최상위 | 배열 | 선택(없으면 `[]`) | 이 의뢰서에 관련된 자재 사용 내역 |
| 마케팅담당자 | 운영통계 행 | 문자열 | 필수 | 담당 직원명 |
| 등록자 | 운영통계 행 | 문자열 | 필수 | 실제 작업 등록자 |

| 작업내역서번호 | 운영통계 행 | 정수 | 필수 | 작업 내역서 고유 번호 |
| 작업내역서 | 운영통계 행 | 문자열 | 필수 | `"거래처명 - 업무상세"` 형식 (앞부분이 거래처명으로 자동 분리됨) |
| 작업명 | 운영통계 행 | 문자열 | 필수 | 작업 세부 분류 |
| 작업내역서상세 | 운영통계 행 | 문자열 | 선택 | 상세 설명 |
| 반제품여부 | 운영통계 행 | 문자열 | 선택(기본 "N") | "Y"면 건수를 0으로 처리(봉입 없음) |
| P수 | 운영통계 행 | 문자열 | 선택 | 건당 장 수 (예: "1P") |
| 장수 | 운영통계 행 | 정수 | 선택(기본 0) | 출력용지 장수 |
| 건수 | 운영통계 행 | 정수 | 선택(기본 0) | 봉입건수 |
| 출력페이지 | 운영통계 행 | 정수 | 선택(기본 0) | 장비출력페이지 |
| 청구페이지 | 운영통계 행 | 정수 | 선택(기본 0) | 실제출력페이지 |
| 작업내역서번호 | 자재 행 | 정수 | 필수 | 어느 작업내역서에 대한 자재인지 |
| 작업일자 | 자재 행 | 문자열 | 필수 | `YYYY-MM-DD` 형식 |
| 자재종류 | 자재 행 | 문자열 | 필수 | `봉투` / `용지` / `삽지` / `미구분` 중 하나 |
| 작업명 | 자재 행 | 문자열 | 선택 | 이 자재 사용이 속한 작업명(없으면 운영통계자료와 작업내역서번호로 추정 매칭 — 아래 요청 참고) |
| 자재명 | 자재 행 | 문자열 | 선택 | (2026-07-19 추가) 자재 원본 이름. `자재종류`가 `봉투`인 행에서 보내주시면 `merge_자재()`가 이름에 "각대"·"대봉투" 포함 여부로 자동 분류합니다 |

| 사용량 | 자재 행 | 정수 | 선택(기본 0) | 자재 사용 수량 |

> 자재사용현황 행에는 업무의뢰서번호를 따로 넣지 않습니다 — 요청 최상위의 업무의뢰서번호에 자동으로 귀속됩니다.

> **✅ 지원 안내 (2026-07-19 갱신):** `자재종류`가 `봉투`인 행에 `자재명` 또는 `자재형태` 필드를 보내주시면 이제 API가 그대로 받아 DB에 저장합니다(둘 다 안 보내면 지금처럼 "일반봉투"로 간주). `자재형태`는 자유 문자열이라 `일반봉투`/`각대대봉투` 외에 `소봉투`/`중봉투`/`대봉투` 같은 값도 저장 자체는 가능합니다.
> **다만 현재는 저장만 되고, 실제 단가 계산(`calc_공급가맵()`)·거래명세서 금액은 여전히 "일반봉투/각대대봉투" 2종 기준으로만 동작합니다.** 그 외 값을 보내주시면 저장은 정확히 되지만 단가는 "각대대봉투가 아니면 일반 단가"로 처리됩니다 — 소/중/대별로 실제 다른 단가를 매기려면 저희 쪽 단가 체계 확장 작업이 추가로 필요합니다(진행 계획: `.claude/plans/plan_봉투크기단가확장.md`). 배치 업로드(`data/자재사용현황.xlsx`)는 이미 자재명 기준으로 정상 처리되고 있습니다.

> **📌 요청 (2026-07-19 추가):** 자재 행에도 `작업명` 필드를 추가로 보내주시면 좋겠습니다. 하나의 작업내역서번호에 작업명이 여러 개 섞여 있는 경우(예: 같은 작업내역서로 여러 건을 함께 처리한 경우), 지금은 이 필드가 없어 저희 쪽에서 운영통계자료와 작업내역서번호로만 추정 매칭하는데, 그 작업내역서에 작업명이 여러 개 걸쳐 있으면 자재 수량이 실제보다 부풀려질 수 있습니다. 배치 업로드(`data/자재사용현황.xlsx`)에는 이미 작업명(작업이름)이 있어 그쪽은 정확히 처리됩니다.

```json
{
  "status": "ok",
  "업무의뢰서번호": "93690",
  "운영통계_반영행수": 1,
```

| 상태 코드 | 상황 | 예시 |
|---|---|---|

| 500 | DB 반영 실패 (서버·DB 문제) | `{"detail": "DB 반영 실패: ..."}` — 이 경우 재시도 요청 |

`거래처마스터` 테이블 전체를 거래처명 순으로 반환. 파라미터 없음.

## 4-2. `GET /단가마스터`

`단가마스터` 테이블 전체를 거래처명·업무명·작업명 순으로 반환. 파라미터 없음. (단가 숫자 정리(NaN→0)는 지금처럼 app.py 쪽에서 처리)

## 4-3. `GET /거래명세서이력`

`거래명세서`(그룹 집계·상태)와 `거래명세서_의뢰서`(의뢰서번호 목록)를 JOIN해서, **업무의뢰서번호 단위로 이미 펼쳐진 상태**로 반환합니다. 구 SQLite 방식(업무의뢰서번호목록을 JSON 문자열로 저장 → 매번 파싱해서 펼침)이 필요 없어졌습니다 — 정규화된 테이블 덕분에 JOIN 한 번으로 대체됩니다.

- `단가`가 등록되지 않은 (거래처,업무명,작업명) 조합은 `/예상공급가액`·Excel 생성과 동일하게 결과에서 제외됩니다.
- **다중 업무명 규칙조회(2026-08-08 재설계)**: 예전엔 여러 업무명이 섞이면 그중 "대표 업무명" 1개로만 규칙을 조회해 나머지 업무명의 저장된 규칙이 누락되는 버그가 있었음. 지금은 `업무명_목록`이 2개 이상이면 그 조합 전용 **통합조건식**(`청구품목통합규칙` 테이블)을 우선 조회하고, 없으면 각 업무명의 개별조건식(`청구품목규칙`)을 병합해 적용함:
  - `규칙출처`: `"통합"`(선택된 업무명 집합과 정확히 일치하는 통합조건식 적용됨) | `"불일치"`(등록된 통합조건식과 부족/초과 차이가 있어 사용자 확인 필요, 아래 `통합조건식_불일치` 참고) | `"개별"`(관련 통합조건식 없음, 개별조건식 병합 결과)
  - `업무명조합_사용중`: `규칙출처="통합"`일 때만 그 조합 문자열(파이프 `|` 결합) — `POST /거래명세서요청` 확정 시 그대로 echo해서 보내야 함
  - `통합조건식_불일치`: `{"상황": "부족"|"초과", "기존업무명조합": "...", "차이_업무명": [...]}` — `"부족"`은 등록된 통합조건식 일부 업무명이 지금 선택에서 빠짐, `"초과"`는 지금 선택이 등록된 통합조건식보다 많음. 이 값이 있으면 화면은 확정을 막고 사용자에게 "제외/추가하고 확정" 선택을 받아야 함(아래 `POST /거래명세서요청`의 `통합조건식_해결` 참고)
- `규칙적용결과`/`규칙목록`/`미분류`/`부가세구분`은 [거래명세서편집_규칙엔진](../.claude/plans/plan_거래명세서편집_규칙엔진.md) 참고. `규칙목록`은 위 판정 결과(통합 또는 개별 병합)로 조회된 재사용 규칙 — 화면이 별도로 재조회할 필요 없이 이 응답 하나로 끝납니다.

### 오류 응답

| 상태 코드 | 상황 |
|---|---|
| 400 | `의뢰서번호_목록`이 비어 있음 |
| 404 | 해당 의뢰서 데이터를 운영통계자료에서 찾을 수 없음 |
| 500 | 단가 미등록 등으로 품목이 하나도 안 만들어짐 |

실제 검증: 기존 발행 건(D-202607-00001)에 연결된 의뢰서 9건으로 직접 호출해 품목·총합계가 정상 반환되는지, 인증 없이 호출 시 401이 반환되는지 확인. `build_품목행()` 분리 리팩터링 자체는 리팩터링 전후 `GET /거래명세서엑셀/{no}` 결과가 바이트 단위로 완전히 동일함을 `hashlib` 비교로 확인(회귀 없음).

## 4-4. 쓰기 API (거래처마스터·단가마스터·거래명세서)

> 금액(공급가액·세액·합계) 계산과 거래명세서 Excel 생성은 `scripts/billing.py`(app.py·이 API 공용)가 담당합니다(2026-07-19부터 — 그 전엔 app.py 전용이었으나 자재형태 컬럼이 MariaDB에 추가되며 API로도 이전됨). 다만 `POST /거래명세서요청`은 여전히 **이미 계산된 값을 받아 저장만** 합니다(화면에서 `/예상공급가액`으로 미리 계산한 값을 그대로 보내는 흐름).

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/거래처마스터` | 거래처 1건 신규 등록 (거래처명 필수·중복 시 409). 등록일·수정일 생략 시 오늘 날짜 (2026-07-19 전체교체→단건생성으로 변경, Next.js [4-D]) |
| PUT | `/거래처마스터/{name}` | 거래처 1건 수정 — **사업자등록번호·수신이메일·비고만** 변경 가능, 거래처명은 요청 바디에 필드 자체가 없어 변경 불가(단가마스터·거래명세서·운영통계자료가 거래처명을 FK 없이 문자열로만 참조하고 있어, 이름이 바뀌면 기존 연결이 조용히 끊어지는 것을 방지) |
| DELETE | `/거래처마스터?거래처명=A&거래처명=B` | 거래처명 목록으로 삭제 |
| POST | `/단가마스터` | 단가 1건 신규 등록 (거래처명 필수, 업무명·작업명은 NULL 가능 = 기본단가, 응답에 신규 `id` 포함) |
| PUT | `/단가마스터/{id}` | 단가 1건 수정 (모든 단가 필드 갱신) |
| DELETE | `/단가마스터?id=1&id=2` | id 목록으로 삭제 |
| POST | `/거래명세서요청` | 채번 후 `거래명세서`+`거래명세서_의뢰서` 저장 |
| POST | `/거래명세서발행` | `발송여부=1`로 변경 |
| POST | `/거래명세서발행취소` | `발송여부=0`으로 되돌림 (원래 계획엔 없었으나 app.py에 이미 있는 "발행 취소" 기능이라 함께 추가) |
| POST | `/거래명세서부분취소` | 선택한 의뢰서만 취소 (2026-07-19 신규, 아래 상세 참고) |

### `POST /거래처마스터` / `PUT /거래처마스터/{name}` 오류 응답 (2026-07-19 신규)

| 상태 코드 | 상황 |
|---|---|
| 400 | 거래처명이 비어 있음 (POST) |
| 409 | 이미 존재하는 거래처명 (POST) |
| 404 | 해당 거래처명이 없음 (PUT) |

### `POST /거래명세서요청` 요청 예시
```json
{
  "거래처명": "BC카드", "사업부": "DM사업부", "담당자": "강서윤",
  "품목": "정기청구(개인일반) 이용대금명세서",
  "공급가액": 193760, "세액": 19376, "합계": 213136,
  "의뢰서번호_목록": ["96193", "96194"]
}
```
응답: `{"status": "ok", "거래명세서번호": "D-202607-00003", "편집여부": 0}`

**규칙 저장 시 업무명_목록 관련 필드 (2026-08-08 다중업무명 규칙조회 재설계)** — `규칙`을 함께 보내 조건식을 새로 만들거나 고칠 때만 의미가 있습니다.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| 업무명_목록 | 배열(문자열) | `규칙`을 보낼 때 필수 | 규칙 저장 키로 쓰이는 업무명 집합(예전 `업무명` 단수 필드 대체). 1개면 개별조건식, 2개 이상이면 통합조건식에 저장됨 |
| 업무명조합_사용중 | 문자열 | 선택 | 미리보기 응답이 `규칙출처="통합"`으로 내려준 그 조합 문자열을 그대로 echo — 정확 일치 상태에서 규칙만 고쳐 재저장할 때 사용 |
| 통합조건식_해결 | `{기존업무명조합: string}` | 선택 | 미리보기가 `통합조건식_불일치`를 내려줬을 때, 화면에서 사용자가 "제외/추가하고 확정"을 눌러 채워짐 — 서버가 `기존업무명조합`을 새 `업무명_목록` 기준으로 **UPDATE**(레코드 삭제 아님, 소속 재조정)한 뒤 그 새 조합에 규칙을 저장함 |

거래처에 이미 부분적으로 겹치는 통합조건식이 남아있는(정상 흐름에선 발생하지 않는) 드문 경우 `통합조건식_해결` 처리 중 `409`(이미 같은 업무명조합의 통합조건식 존재)가 날 수 있습니다.

**거래명세서는 항상 1건만 생성됩니다(2026-08-01)** — `품목_최종`의 각 행에 실린 `조`(Optional, 시트명)는 `거래명세서_품목`에 그대로 저장해두고, 다운로드 시점(`GET /거래명세서엑셀/{no}`)에 그 값으로 시트를 나눠 통합 엑셀을 만드는 데만 씁니다. (2026-07-29~2026-08-01엔 조가 2개 이상이면 거래명세서 자체를 조 개수만큼 각각 채번·저장했었으나, 실사용 중 "발행요청목록에 번호가 여러 개 생겨 불편하다"는 피드백으로 변경 — 그 시절 만들어진 기존 발행 건은 `거래명세서.묶음번호`로 여전히 인식·다운로드됩니다, `GET /거래명세서엑셀/{no}` 참고.)

### `POST /거래명세서요청` 오류 응답

| 상태 코드 | 상황 |
|---|---|
| 400 | `의뢰서번호_목록`이 비어 있음 |
| 400 | `의뢰서번호_목록`에 속한 의뢰서들의 사업부가 서로 다름 (2026-07-19 신규 — 서버가 `운영통계자료`를 조회해 재검증. app.py 화면단 검증과 별개의 방어선) |
| 400 | `의뢰서번호_목록`에 속한 의뢰서들의 거래처명이 서로 다름 (2026-08-08 신규 — 통합조건식 키가 (거래처명,업무명조합)이라 거래처명 혼합을 함께 방어) |
| 409 | 통합조건식_해결 처리 중 목표 업무명조합이 이미 별도 레코드로 존재 (정상 흐름에선 발생하지 않는 안전망) |
| 500 | DB 오류 등 |

### `POST /거래명세서부분취소` (2026-07-19 신규)

거래명세서_의뢰서 중 선택한 의뢰서번호만 취소합니다. 남는 의뢰서가 0건이면 거래명세서 행 자체를 삭제(FK가 `ON DELETE CASCADE`라 `거래명세서_의뢰서`도 자동 정리 → 미발행 목록으로 자연 복귀), 1건 이상 남으면 취소분만 삭제하고 품목·담당자·공급가액·세액·합계를 재계산해 갱신합니다. 이미 발행완료(`발송여부=1`)된 거래명세서는 취소할 수 없습니다.

요청 예시:
```json
{
  "거래명세서번호": "D-202607-00003",
  "의뢰서번호_목록": ["96193"]
}
```
응답: `{"status": "ok", "action": "delete"|"update", "거래명세서번호": "D-202607-00003", "남은건수": 0}`

오류 응답:

| 상태 코드 | 상황 |
|---|---|
| 400 | `의뢰서번호_목록`이 비어 있음 |
| 400 | 이미 발행완료(`발송여부=1`)된 거래명세서를 취소 시도 |
| 400 | `의뢰서번호_목록`에 이 거래명세서번호에 속하지 않는 의뢰서번호가 포함됨 |
| 404 | 해당 거래명세서번호가 없음 |
| 500 | DB/재계산 오류 등 |

실제 테스트로 요청→발행목록 반영→전체취소(action=delete)→미발행목록 복귀→`거래명세서`·`거래명세서_의뢰서` 완전 삭제(CASCADE)까지 전체 흐름 확인 완료.

### 기본단가 중복 방지 (2026-07-19, Next.js "단가관리" 화면과 함께 해결)
`단가마스터`의 UNIQUE(거래처명, 업무명, 작업명) 제약은 업무명·작업명이 **둘 다 NULL(거래처 전체 기본단가)이거나 업무명만 있고 작업명이 NULL(업무명 단위 기본단가)일 때는 중복을 막지 못했습니다** — MariaDB는 NULL끼리 서로 다른 값으로 취급하기 때문입니다(기존 SQLite도 동일). `POST /단가마스터`가 이제 작업명이 NULL인 모든 경우(업무명 유무 무관)에 INSERT 전 직접 중복 확인 후 409를 반환하도록 보완됨. 응답에도 새로 생성된 행의 `id`가 함께 반환됨(`{"status":"ok","id":123}`) — 이전엔 `id` 없이 `{"status":"ok"}`만 반환했음.
