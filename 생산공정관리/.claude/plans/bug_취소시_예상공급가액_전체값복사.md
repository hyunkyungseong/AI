# 버그 수정: 발행 취소·확정 시 "거래명세서 전체 총액"(또는 개별 의뢰서 몫)이 잘못된 곳에 복사됨

> 상태: ✅ 완료 — 코드 수정·검증·사무실 PC 배포·GitHub 커밋/푸시(`e87494d`)까지 전부 완료(2026-08-23).
> 오늘 만든 `bug_예상공급가액_부가세미반영.md`(발행목록 예상공급가액을 "기준" 스냅샷 기반으로 변경)의
> 직접적인 회귀. 사용자가 실제 화면(취소→미발행목록 19건 전부 16,852,782원으로 동일 표시, 이어서
> 재요청→발행요청목록 "수정전공급가액"이 미발행목록 시절 개별값의 합인 16,852,117원으로 표시)으로
> 두 차례에 걸쳐 발견.

## Context — 왜 필요한가

사용자가 미발행목록에서 현대해상 자동차증권 19건을 선택했는데, 서로 다른 청구페이지·장수를 가진
행들인데도 "예상공급가액"이 전부 16,852,782원으로 똑같이 나왔다고 제보. 발행요청목록의
"수정전공급가액"도 320,202,858원(=19×16,852,782)으로 나와 의심스럽다고 함.

## 원인 (실제 DB·API 직접 호출로 검증 완료)

1. `GET /발행목록`(백엔드)을 직접 호출해 확인 — **정상**. 현대해상 자동차증권 미발행 42건을
   조회해보니 전부 서로 다른 값(437,302 / 476,235 / 519,175원 등)을 정확히 반환.
2. 그런데 `frontend/components/Tab4IssuedList.tsx`의 발행 취소 처리(`onReturnToUnissued`)가
   `발행행.예상공급가액`을 그대로 개별 `미발행행.예상공급가액`으로 복사하고 있었음. 오늘 만든
   `bug_예상공급가액_부가세미반영.md` 수정으로 `발행행.예상공급가액`의 **의미가 바뀌었다** —
   예전엔 `calc_공급가맵()` 기반 "그 의뢰서 하나만의" 값이었는데, 오늘부터는 "그 의뢰서가 속한
   거래명세서 전체 총액"(거래명세서번호 단위로 계산해 속한 모든 의뢰서 라인에 동일하게 반복
   표시)으로 바뀌었음 — 이 취소 로직은 예전 의미를 그대로 믿고 복사하다 보니, 취소돼 미발행으로
   돌아간 19건 전부에 "그 거래명세서 19건 전체 몫"이 개별 값인 것처럼 잘못 붙었음.
3. 게다가 `Tab4.tsx`는 "거래명세서 관리" **최상위 탭에 새로 진입할 때만** 미발행목록을 서버에서
   다시 받아온다(2026-08-09 설계) — 발행요청목록→미발행목록처럼 **같은 최상위 탭 안에서 서브탭만
   전환**하면 이 재조회가 트리거되지 않아, 취소 시 만들어진 잘못된 값이 화면에 그대로 남아있었음.

## 수정

- `frontend/components/Tab4IssuedList.tsx` — 취소 시 되돌리는 미발행행의 `예상공급가액`을
  `r.예상공급가액`(더 이상 신뢰할 수 없는 값) 대신 `null`로 설정(잠깐 "⚠️ 미등록"으로 보이는 것은
  감수 — 곧바로 아래 재조회가 정확한 값으로 덮어씀).
- `frontend/components/Tab4.tsx` — 미발행목록 서버 재조회 로직(`useEffect` 안 인라인)을
  `refreshInvoice` 콜백으로 추출하고, `handleReturnToUnissued`(발행 취소 콜백)에서도 낙관적
  업데이트 직후 이 함수를 호출 — 서브탭 전환 여부와 무관하게 취소 즉시 서버의 정확한 개별 값으로
  갱신됨.

## D-202608-00094(사용자가 실제로 만든 거래명세서)는 재정산 필요 없음

우연처럼 보였지만, `build_품목행()`으로 이 19개 의뢰서(94880, 95886~95903)를 직접 재계산해보니
정확히 18,538,060원(부가세 분리 후 16,852,782원)이 나왔다 — 즉 **D-202608-00093과 D-202608-00094는
실제로 완전히 같은 19개 의뢰서였다**(사용자가 한 번 요청→취소→같은 항목을 다시 요청). 우연의 일치가
아니라 같은 데이터를 두 번 확정한 것. `POST /거래명세서요청`은 매번 서버가 운영통계자료부터 직접
재계산하므로(프론트의 버그와 무관한 경로), D-202608-00094에 저장된 공급가액(16,852,782원)은
실제로 정확한 값 — 재정산 불필요.

## 후속 발견 — 확정(요청) 직후에도 동일한 클래스의 버그 ✅ 완료 (같은 날)

사용자가 재요청(D-202608-00095) 후 화면 재확인 중 "수정전공급가액이 여전히 미발행목록의 원본으로
보인다"고 재차 제보. 실제 DB(`거래명세서_품목` 구분='기준' 합계=18,538,060)와 로컬 API 직접 호출
(`/발행목록`이 `"예상공급가액": 16852782`를 정확히 반환)로 **백엔드는 완전히 정상**임을 재확인 —
문제는 또 다른 프론트엔드 낙관적 업데이트였음.

**원인 2**: `Tab4Invoice.tsx`의 "확정" 처리(`onIssued(...)` 호출부)가 `selectedRows`(미발행행,
개별·조건식 미적용 예상공급가액)를 `...r`로 스프레드해 새 발행행을 만드는데, 명시적으로 덮어쓰는
필드 목록에 `예상공급가액`이 빠져 있어 **원래 개별 값이 그대로 남음**. 발행요청목록의 레벨1(그룹)
테이블은 `frontend/lib/issuedGrouping.ts`가 그룹 내 여러 라인의 예상공급가액을 **합산**하므로,
19개의 서로 다른(그러나 전부 "조건식 미적용 개별" 기준인) 값을 더한 16,852,117원이 "그룹 예상
공급가액"으로 잘못 표시됨 — 취소 버그와 정확히 같은 클래스(스코프가 다른 필드를 그대로 물려받음).

**수정**:

  ①"거래명세서 관리" 최상위 탭 재진입 시 `refreshInvoice()`와 함께 호출 ②확정 성공
  직후(`handleIssued`)에도 낙관적 업데이트 직후 호출 — 서버의 정확한 거래명세서 단위 값으로 즉시

## 진짜 근본 원인 — `issuedGrouping.ts`가 "거래명세서 단위 반복값"을 다시 합산하고 있었음 ✅ 완료 (같은 날)

위의 낙관적 업데이트 수정(취소·확정 시 null+재조회, cache:no-store, 부분취소 refreshIssued 추가)을
전부 반영한 뒤에도, **시크릿 창(캐시·세션 완전 배제)에서 처음부터 다시 확정해도 320,202,858원이
재현**된다는 사용자 제보로 진짜 원인을 재조사 — `frontend/lib/issuedGrouping.ts`의
`build레벨1그룹()`을 직접 열어보니:

```ts
예상공급가액: 단가미등록있음 ? null : sum((l) => l.예상공급가액 ?? 0),   // 57행, 수정 전
```

바로 위 63행의 `확정공급가액: lines[0].확정공급가액`(거래명세서번호 단위 값이라 그룹 내 모든
라인이 항상 동일 — "아무 라인이나 대표로 사용", 합산 안 함)과 **똑같이 처리했어야 하는데**,
`예상공급가액`만 `sum()`으로 **합산**하고 있었다. 이건 `bug_예상공급가액_부가세미반영.md`
이전(예상공급가액이 "의뢰서 개별 몫"이던 시절)엔 맞는 로직이었지만, 그 수정으로 API가
"거래명세서 전체 총액을 그 거래명세서에 속한 모든 의뢰서 라인에 동일하게 반복"하는 방식으로
바뀐 뒤로는 **의뢰서 건수(19건)만큼 부풀려지는 버그**가 됐다 — 서버가 아무리 정확한 값
(16,852,782)을 19번 반복해서 내려줘도, 여기서 19번 또 더하면 항상 19배(320,202,858)가 된다.

이게 진짜 원인이었다 — 지금까지 고친 낙관적 업데이트(취소·확정 시 null 처리, refreshInvoice/
refreshIssued, cache:no-store)는 전부 그 자체로는 정당한 개선이었지만, 이 그룹화 버그 앞에서는
**서버가 아무리 정확한 값을 줘도 화면에서 다시 부풀려졌기 때문에** 효과가 없었다.

**수정**: `frontend/lib/issuedGrouping.ts` — `예상공급가액: sum((l) => l.예상공급가액 ?? 0)` →
`예상공급가액: lines[0].예상공급가액`(확정공급가액과 동일한 "대표값 하나" 패턴).
