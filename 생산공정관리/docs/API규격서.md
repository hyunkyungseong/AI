# 생산공정관리 대시보드 — API 규격서

> 당사 생산공정관리시스템 개발 담당자에게 전달할 연동 문서입니다.
> 서버 코드: `scripts/api.py` (FastAPI) | 실행: `python scripts/api.py` (포트 8000)
> 이 문서는 API가 추가될 때마다 함께 갱신합니다. (최종 갱신: 2026-07-19)

---

## 1. 연동 방식 개요

- **방향: Push** — 당사 생산공정관리시스템이 업무의뢰서 처리를 완료할 때마다, 이 서버의 API를 호출해서 데이터를 보내주는 방식입니다. (우리 쪽이 주기적으로 가지러 가는 방식이 아닙니다)
- **전송 단위: 업무의뢰서(건) 단위, 실시간** — 업무의뢰서 하나가 완료되면, 그 의뢰서에 속한 **모든 작업내역 행을 한 번에** 호출 1건으로 보내주셔야 합니다. (한 의뢰서의 행을 여러 번 나눠 보내면 금액 계산이 틀어집니다 — 3번 항목 참고)
- **현재 서버 주소:** `http://localhost:8000` (로컬 개발 중, 사무실 PC 이관 후 주소 확정 예정)
- **인증 (2026-07-19 확정):** `/운영통계자료수신`은 **`X-API-Key` 헤더**(고정 키, `db_config.py`의 `API_KEY` 값)로 인증합니다. 사람이 로그인하는 방식(2번 참고)과는 별개입니다 — 시스템 간 연동이라 계정이 필요 없습니다.

## 2-1. 로그인 인증 (화면용 API 전체 공통, 2026-07-19 추가)

> `/health`, `/운영통계자료수신`을 제외한 모든 API는 로그인 토큰이 필요합니다. 계정은 담당자별 개별 계정이며, 관리자가 `python scripts/create_user.py`로 생성합니다 (아직 화면 UI 없음).

### `POST /login`

**요청**
```json
{"사용자명": "gsyoon", "비밀번호": "********"}
```

**응답 (200)**
```json
{"access_token": "eyJhbGciOi...", "token_type": "bearer", "이름": "강서윤"}
```

**응답 (401)** — 사용자명 또는 비밀번호가 틀린 경우
```json
{"detail": "사용자명 또는 비밀번호가 올바르지 않습니다"}
```

### 이후 모든 요청에 토큰 첨부

```
Authorization: Bearer eyJhbGciOi...
```

- 토큰 유효시간: 12시간 (만료되면 다시 `/login` 호출)
- 토큰 없이/잘못된 토큰으로 호출 시 401 반환

## 3. `GET /summary`

`운영통계자료` 테이블을 (사업부 조건만 선택적으로 걸어서) 원본 그대로 반환합니다.

> **설계 방식(A안):** 탭1·2·3의 전월대비·거래처별/담당자별 집계 로직은 이 API로 옮기지 않고, 지금처럼 `app.py`(pandas)가 그대로 담당합니다. 이 API는 "데이터를 어디서 가져오는지"만 pkl 파일 → API 호출로 바꿔주는 역할입니다. 집계 로직을 그대로 재사용해 위험을 최소화하기 위한 선택입니다.

### 요청

| 파라미터 | 위치 | 필수 | 설명 |
|---|---|---|---|
| 사업부 | 쿼리스트링 | 선택 | `DM사업부` / `N사업부` 중 하나 이상. 생략하면 전체 반환. 예: `/summary?사업부=DM사업부&사업부=N사업부` |

### 응답 (200)

`운영통계자료` 테이블의 각 행을 JSON 객체로 담은 배열. 컬럼 구성은 KNOWLEDGE.md "운영통계자료 MariaDB 테이블 스키마" 참고 (`id` 포함, app.py 쪽에서는 사용하지 않아도 무방).

```json
[
  {"id": 1, "마케팅담당자": "강서윤", "등록자": "강서윤명", "업무명": "정기청구서",
   "업무의뢰서번호": "93690", "작업일자": "2026-03-02T22:05:08", ...},
  ...
]
```

### 성능 참고 (2026-07-19 측정)
- 전체(36,804행) 응답: 약 2초, 약 27MB
- 사업부 필터 적용 시(예: DM사업부 24,679행) 데이터량에 비례해 축소
- 사내망 내부 도구 기준으로는 허용 가능한 수준이나, 나중에 체감 속도 문제가 생기면 기간(날짜 범위) 필터 파라미터 추가를 검토

## 4. `POST /운영통계자료수신`

업무의뢰서 하나에 속한 작업내역·자재사용량 데이터를 수신합니다.

### ⚠️ 반드시 지켜야 할 것
- **같은 업무의뢰서번호에 속한 행은 반드시 한 번의 호출에 전부 포함**해서 보내주세요. 일부만 보내고 나중에 나머지를 따로 보내면, 청구페이지 합산 금액이 잘못 계산됩니다.
- **같은 업무의뢰서번호로 다시 호출하면, 기존에 저장된 그 의뢰서의 데이터는 전부 지워지고 새로 보낸 내용으로 완전히 교체**됩니다. (수정·정정 시 안전하게 재전송 가능)
- **인증 필수 (2026-07-19 추가):** 요청 헤더에 `X-API-Key: <전달받은 키 값>`을 반드시 포함해야 합니다. 키가 없거나 틀리면 401 오류가 반환됩니다. (로그인 방식이 아닙니다 — 2-1번 항목과 다름)

### 요청 (Request Body, JSON)

```json
{
  "업무의뢰서번호": "93690",
  "운영통계": [
    {
      "마케팅담당자": "강서윤",
      "등록자": "강서윤",
      "업무명": "정기청구서",
      "작업일자": "2026-07-19 10:00:00",
      "작업내역서번호": 12345,
      "작업내역서": "거래처명 - 업무상세내용",
      "작업명": "개인일반",
      "작업내역서상세": "상세 설명 (선택)",
      "반제품여부": "N",
      "P수": "1P",
      "장수": 100,
      "건수": 50,
      "출력페이지": 100,
      "청구페이지": 100
    }
  ],
  "자재사용현황": [
    {
      "작업내역서번호": 12345,
      "작업일자": "2026-07-19",
      "자재종류": "봉투",
      "사용량": 50
    }
  ]
}
```

### 필드 설명

| 필드 | 위치 | 타입 | 필수 | 설명 |
|---|---|---|---|---|
| 업무의뢰서번호 | 최상위 | 문자열 | 필수 | 이 요청 전체가 속한 업무의뢰서번호 (숫자처럼 보여도 문자열로 보내주세요) |
| 운영통계 | 최상위 | 배열 | 필수(1개 이상) | 이 의뢰서에 속한 작업내역 행 목록 |
| 자재사용현황 | 최상위 | 배열 | 선택(없으면 `[]`) | 이 의뢰서에 관련된 자재 사용 내역 |
| 마케팅담당자 | 운영통계 행 | 문자열 | 필수 | 담당 직원명 |
| 등록자 | 운영통계 행 | 문자열 | 필수 | 실제 작업 등록자 |
| 업무명 | 운영통계 행 | 문자열 | 필수 | 업무 분류명 |
| 작업일자 | 운영통계 행 | 문자열 | 필수 | `YYYY-MM-DD HH:MM:SS` 형식 권장 |
| 작업내역서번호 | 운영통계 행 | 정수 | 필수 | 작업 내역서 고유 번호 |
| 작업내역서 | 운영통계 행 | 문자열 | 필수 | `"거래처명 - 업무상세"` 형식 (앞부분이 거래처명으로 자동 분리됨) |
| 작업명 | 운영통계 행 | 문자열 | 필수 | 작업 세부 분류 |
| 작업내역서상세 | 운영통계 행 | 문자열 | 선택 | 상세 설명 |
| 반제품여부 | 운영통계 행 | 문자열 | 선택(기본 "N") | "Y"면 건수를 0으로 처리(봉입 없음) |
| P수 | 운영통계 행 | 문자열 | 선택 | 건당 장 수 (예: "1P") |
| 장수 | 운영통계 행 | 정수 | 선택(기본 0) | 출력용지 장수 |
| 건수 | 운영통계 행 | 정수 | 선택(기본 0) | 봉입건수 |
| 출력페이지 | 운영통계 행 | 정수 | 선택(기본 0) | 장비출력페이지 |
| 청구페이지 | 운영통계 행 | 정수 | 선택(기본 0) | 실제출력페이지 |
| 작업내역서번호 | 자재 행 | 정수 | 필수 | 어느 작업내역서에 대한 자재인지 |
| 작업일자 | 자재 행 | 문자열 | 필수 | `YYYY-MM-DD` 형식 |
| 자재종류 | 자재 행 | 문자열 | 필수 | `봉투` / `용지` / `삽지` / `미구분` 중 하나 |
| 사용량 | 자재 행 | 정수 | 선택(기본 0) | 자재 사용 수량 |

> 자재사용현황 행에는 업무의뢰서번호를 따로 넣지 않습니다 — 요청 최상위의 업무의뢰서번호에 자동으로 귀속됩니다.

> **📌 요청 (2026-07-19 추가):** `자재종류`가 `봉투`인 행은 일반봉투/각대대봉투에 따라 단가가 다른데, 지금 이 요청에는 그 구분이 없어 저희 쪽에서 일단 "일반봉투"로 간주해 처리하고 있습니다. 가능하시면 자재 행에 `자재명`(또는 `자재형태`: `일반봉투`/`각대대봉투`) 필드를 추가로 보내주시면 각대대봉투 건도 정확히 계산됩니다. 배치 업로드(`data/자재사용현황.xlsx`)에는 이미 자재명이 있어 그쪽은 정상 처리됩니다.

### 응답 (성공, 200)

```json
{
  "status": "ok",
  "업무의뢰서번호": "93690",
  "운영통계_반영행수": 1,
  "자재사용현황_반영행수": 1
}
```

### 오류 응답

| 상태 코드 | 상황 | 예시 |
|---|---|---|
| 400 | `운영통계` 배열이 비어 있음 | `{"detail": "운영통계 배열이 비어 있습니다"}` |
| 422 | 필수 필드 누락·타입 오류 (FastAPI 자동 검증) | 필드별 오류 상세 반환 |
| 500 | DB 반영 실패 (서버·DB 문제) | `{"detail": "DB 반영 실패: ..."}` — 이 경우 재시도 요청 |

## 4-1. `GET /거래처마스터`

`거래처마스터` 테이블 전체를 거래처명 순으로 반환. 파라미터 없음.

## 4-2. `GET /단가마스터`

`단가마스터` 테이블 전체를 거래처명·업무명·작업명 순으로 반환. 파라미터 없음. (단가 숫자 정리(NaN→0)는 지금처럼 app.py 쪽에서 처리)

## 4-3. `GET /거래명세서이력`

`거래명세서`(그룹 집계·상태)와 `거래명세서_의뢰서`(의뢰서번호 목록)를 JOIN해서, **업무의뢰서번호 단위로 이미 펼쳐진 상태**로 반환합니다. 구 SQLite 방식(업무의뢰서번호목록을 JSON 문자열로 저장 → 매번 파싱해서 펼침)이 필요 없어졌습니다 — 정규화된 테이블 덕분에 JOIN 한 번으로 대체됩니다.

> 원래 계획에는 `/미발행목록`·`/발행요청목록` 2개로 나뉘어 있었으나, 정규화 이후 두 화면 모두 이 API 하나의 결과만 있으면 app.py(pandas)에서 계산 가능해서 하나로 통합했습니다 (A안과 동일한 설계 철학 — 계산은 app.py, API는 원본 데이터 제공).

### 요청

| 파라미터 | 위치 | 필수 | 설명 |
|---|---|---|---|
| 발송여부 | 쿼리스트링 | 선택 | `0`(발행대기) 또는 `1`(발행완료)로 필터. 생략하면 전체 반환 |

### 응답 (200)

```json
[
  {
    "거래명세서번호": "D-202607-00002",
    "거래처명": "BC카드",
    "담당자": "강서윤",
    "발행일자": "2026-07-17",
    "품목": "정기청구(개인일반) 이용대금명세서",
    "공급가액": 193760.0,
    "세액": 19376.0,
    "합계": 213136.0,
    "발송여부": 0,
    "발송일": null,
    "파일경로": null,
    "등록일": "2026-07-17T15:41:30",
    "업무의뢰서번호": "96193"
  }
]
```

- **미발행 목록 계산 방법:** `/summary`로 받은 전체 의뢰서번호 중, 이 API 결과에 등장하는 `업무의뢰서번호` 집합에 없는 것들이 미발행 (발송여부와 무관하게 이 목록에 있으면 이미 발행요청된 것)
- **발행요청목록/발행완료 화면:** `발송여부=0`/`발송여부=1`로 필터해서 사용 (또는 전체를 받아 app.py에서 필터링해도 무방)

- 계산에 필요한 자재 수량은 MariaDB `자재사용현황`을 `운영통계자료`와 조인해서 구합니다(자재형태 컬럼, 2026-07-19 추가).

## 4-3c. `GET /거래명세서엑셀/{no}` (2026-07-19 신규)

거래명세서 Excel 파일을 생성해 다운로드로 반환합니다(`scripts/billing.py`의 `generate_거래명세서_excel()` 재사용, app.py와 완전히 동일한 결과물). **발행 시점이 아니라도 언제든 재호출 가능** — app.py는 발행 버튼을 누른 세션에만 파일을 임시로 들고 있지만, 이 API는 그때그때 다시 만들어주므로 발행완료 건은 새로고침 후에도 재다운로드할 수 있습니다.

### 요청

| 파라미터 | 위치 | 필수 | 설명 |
|---|---|---|---|
| no | 경로 | 필수 | 거래명세서번호, 예: `D-202607-00003` (파라미터명이 영문인 이유: Starlette가 `{한글이름}` 형식의 경로 파라미터를 인식하지 못해 라우팅이 항상 실패하는 문제가 있어, 다른 API의 `{id}`처럼 영문으로 통일) |

### 응답 (200)

`Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` 로 xlsx 파일 바이너리를 그대로 반환(`Content-Disposition: attachment`).

### 오류 응답

| 상태 코드 | 상황 |
|---|---|
| 404 | 거래명세서번호가 없거나, 연결된 업무의뢰서가 없거나, 그 의뢰서 데이터를 운영통계자료에서 찾을 수 없음 |
| 500 | 단가 미등록 등으로 Excel 생성 실패 |

## 4-4. 쓰기 API (거래처마스터·단가마스터·거래명세서)

> 금액(공급가액·세액·합계) 계산과 거래명세서 Excel 생성은 `scripts/billing.py`(app.py·이 API 공용)가 담당합니다(2026-07-19부터 — 그 전엔 app.py 전용이었으나 자재형태 컬럼이 MariaDB에 추가되며 API로도 이전됨). 다만 `POST /거래명세서요청`은 여전히 **이미 계산된 값을 받아 저장만** 합니다(화면에서 `/예상공급가액`으로 미리 계산한 값을 그대로 보내는 흐름).

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/거래처마스터` | 거래처마스터 **전체 교체** (배열 전달, 기존 app.py의 일괄 저장 방식과 동일 — DELETE 후 재삽입). 등록일·수정일 생략 시 오늘 날짜 |
| DELETE | `/거래처마스터?거래처명=A&거래처명=B` | 거래처명 목록으로 삭제 |
| POST | `/단가마스터` | 단가 1건 신규 등록 (거래처명 필수, 업무명·작업명은 NULL 가능 = 기본단가) |
| PUT | `/단가마스터/{id}` | 단가 1건 수정 (모든 단가 필드 갱신) |
| DELETE | `/단가마스터?id=1&id=2` | id 목록으로 삭제 |
| POST | `/거래명세서요청` | 채번 후 `거래명세서`+`거래명세서_의뢰서` 저장 |
| POST | `/거래명세서발행` | `발송여부=1`로 변경 |
| POST | `/거래명세서발행취소` | `발송여부=0`으로 되돌림 (원래 계획엔 없었으나 app.py에 이미 있는 "발행 취소" 기능이라 함께 추가) |

### `POST /거래명세서요청` 요청 예시
```json
{
  "거래처명": "BC카드", "사업부": "DM사업부", "담당자": "강서윤",
  "품목": "정기청구(개인일반) 이용대금명세서",
  "공급가액": 193760, "세액": 19376, "합계": 213136,
  "의뢰서번호_목록": ["96193", "96194"]
}
```
응답: `{"status": "ok", "거래명세서번호": "D-202607-00003"}`

### ⚠️ 테스트 중 확인된 특이사항 (신규 버그 아님 — 기존 SQLite와 동일한 동작)
`단가마스터`의 UNIQUE(거래처명, 업무명, 작업명) 제약은 업무명·작업명이 **둘 다 NULL(기본단가)일 때는 중복을 막지 못합니다** — MariaDB/SQLite 모두 NULL끼리는 서로 다른 값으로 취급하기 때문입니다. 같은 거래처에 기본단가를 두 번 등록해도 API가 막아주지 않으므로, 화면(app.py)에서 "이미 기본단가가 있는지" 확인 후 등록하도록 안내하는 것이 안전합니다.

## 5. 참고 — 처리 과정에서 자동으로 계산되는 값

아래 값들은 보내주실 필요 없이, 서버에서 자동으로 계산해 저장합니다:
- **거래처명·업무명상세**: `작업내역서` 필드를 `" - "` 기준으로 분리해서 자동 추출
- **사업부**: `마케팅담당자` 기준으로 자동 분류
- **연월·날짜·시간대**: `작업일자` 기준으로 자동 파생
- **확정청구페이지**: 같은 업무의뢰서번호+업무명 그룹 전체를 보고 3가지 규칙 중 하나로 자동 계산 (그래서 그룹의 모든 행을 함께 보내주셔야 합니다)
- **봉투_사용량·용지_사용량·삽지_사용량·미구분_사용량**: `자재사용현황` 배열을 자재종류별로 자동 집계
