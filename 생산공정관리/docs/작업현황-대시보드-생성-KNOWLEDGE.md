## 🔄 핵심 업무 흐름

```
[운영통계자료.xlsx 업데이트]
         ↓
[데이터갱신_후_실행.bat 실행 → preprocess.py 자동 처리]
         ↓
[대시보드에서 작업 현황 확인]
         ↓
[마케팅 담당자: 미발행 목록에서 의뢰서 선택]
  → "거래명세서 요청" 버튼 클릭 (거래명세서번호 자동 채번)
         ↓
[거래명세서이력 DB에 발행대기(발행여부=0) 저장 → 미발행 목록에서 즉시 제거]
         ↓
[경영지원부 담당자: 발행요청목록(발행대기 건만 표시)에서 검색]
  → 의뢰서번호를 파이프(`|`) 구분으로 발행요청목록 상단 검색창에 입력 → "검색" 버튼 클릭
  → 합계(장수·봉입건수·출력페이지·청구페이지) 확인
         ↓
[이상 없으면 "거래명세서 발행" 버튼 클릭 → 발행완료(발행여부=1) 업데이트 → 발행완료 탭으로 이동]
         ↓
[거래명세서 Excel 생성 → 고객사에 이메일 발송 (미구현)]
```

- **미발행 건:** 거래명세서이력 DB에 등록되지 않은 업무의뢰서 (발행여부 관계없이 이력에 있으면 미발행 목록에서 제외)
- **발행여부 값:** `0` = 발행대기 (마케팅 요청됨, 발행요청목록 탭에 표시), `1` = 발행완료 (경영지원부 처리됨, 발행완료 탭에 표시)
- **담당자 역할 분리:** 마케팅 담당자(요청) ↔ 경영지원부 담당자(검토·발행)
- **의뢰서번호 검색 형식:** 발행요청목록/발행완료 탭 검색창은 파이프(`|`) 구분 한 줄 문자열로 입력 (미발행 목록에는 검색·복사 기능 없음, 2026-07-17 삭제)
- **발행요청목록 탭 (발행대기 전용):** "취소" 버튼(레벨1·레벨2)으로 의뢰서를 미발행 목록으로 되돌림 (복구 불가). 부분 취소 규칙은 아래 "부분 취소" 항목 참고
- **발행완료 탭 (신규):** "발행 취소" 버튼으로 발송여부만 0으로 되돌림 → 발행요청목록 탭에 발행대기 상태로 다시 나타남 (거래명세서이력 행은 유지)
- **필터 적용 범위:** 발행요청목록·발행완료 두 탭 모두 사이드바 전체 필터(사업부·기간·거래처·담당자·업무명) 적용 (`_render_발행_섹션()` 공통 함수, `scripts/app.py`)
- **거래명세서번호 채번 규칙 (2026-07-17 추가):** 형식 `D(또는N)-yyyymm-00001`
  - `D`=DM사업부, `N`=N사업부, `yyyymm`=요청 시점(오늘) 연월, 뒤 5자리는 사업부·연월별 순번
  - "거래명세서 요청" 클릭 시 `_발급_거래명세서번호()`(`scripts/app.py`)가 `거래명세서번호_카운터` 테이블(사업부·연월별 마지막순번)에서 자동 발급
  - **취소해도 번호는 재사용하지 않음** (카운터는 증가만 함 → 결번 허용, 회계 추적용)
  - 선택 항목의 사업부가 섞여 있으면(DM/N 혼합) "거래명세서 요청" 클릭 시 경고만 표시되고 요청이 진행되지 않음 (번호는 사업부 하나에만 귀속) — 2026-07-17부터 버튼 자체를 비활성화하지 않고 항상 눌러지되 클릭 시 검증하는 방식으로 변경 (아래 "버튼 배치" 항목 참고)
- **발행요청목록·발행완료 화면 구조 (2026-07-17, 3단계 드릴다운):** 의뢰서번호를 전부 나열하던 방식에서 아래 3단으로 개편
  1. **레벨1 (요약, 항상 표시)** — 거래명세서번호+업무명 기준 합산 (건수·합계만). "거래명세서 발행" 버튼(발행대기 탭)·"발행 취소"(되돌리기, 발행완료 탭)는 여기서 체크한 그룹 전체 단위로 동작. **"취소"**(발행대기 탭)는 체크한 그룹에 속한 의뢰서를 일괄 취소
  2. **레벨2 (목록, 레벨1 체크 시 표시)** — 체크한 그룹에 속한 의뢰서번호별 행. 발행완료 탭에서는 조회(레벨3 표시) 전용이지만, **발행대기 탭에서는 "취소" 버튼이 있어 개별 의뢰서번호만 선택 취소 가능**
  3. **레벨3 (상세, 레벨2 체크 시 표시)** — 체크한 의뢰서의 원본 작업내역
  - 그룹 기준은 화면에는 "거래명세서번호"로 보이지만 내부적으로는 `_이력_id`(거래명세서이력.id)
  - "거래명세서 발행"·"발행 취소"(되돌리기)는 항상 `_이력_id` 단위 전체로 실행 (레벨1에서 일부 업무명만 체크해도 같은 이력에 묶인 나머지 의뢰서까지 함께 처리됨)
- **부분 취소 ("행 축소" 방식, 2026-07-17 추가):** "취소"(레벨1·레벨2 모두)는 이력 행 전체를 지우지 않고, 취소분이 그 이력의 전체 의뢰서 목록과 같을 때만 `DELETE`(거래명세서번호 결번)합니다. 일부만 취소하면 `업무의뢰서번호목록`에서 취소분만 빼고 `UPDATE`(품목·담당자·공급가액·세액·합계는 `calc_공급가맵()`으로 재계산) — 거래명세서번호는 그대로 유지되고 남은 의뢰서는 같은 번호로 발행요청목록에 남습니다. 계산·확인은 `_render_발행_섹션()` 내부의 `_취소_변경계획()` 헬퍼와 `_부분취소_dialog()`(`scripts/app.py`) 담당. 장기적으로는 MariaDB 전환 시 `거래명세서이력`을 의뢰서번호 단위로 정규화해 이 임시 방식을 대체할 예정 (`.claude/plans/plan_1단계_MariaDB전환.md`)
- **버튼 배치 (2026-07-17 개편):** 미발행 목록의 "거래명세서 요청", 발행요청목록/발행완료 레벨1·레벨2의 액션 버튼(발행/취소/되돌리기)은 모두 표(그리드) **위쪽**에 항상 표시됩니다. 선택 없이 클릭하면 "선택된 항목이 없습니다" 안내만 뜨고 아무 동작도 하지 않습니다 (기존엔 표 아래에 선택 시에만 나타났음). "거래명세서 다운로드" 버튼은 발행요청목록에서 빠지고 **발행완료 탭 전용**으로 이동했습니다 — "거래명세서 발행"을 누르면 바로 발행완료 탭에서 다운로드할 수 있습니다.

> **서버 위치:** 사무실 PC 계속 사용 (MariaDB·FastAPI 상주). **보안:** 사내 전용, 로그인 필요 (거래처 단가·매출 등 민감정보)

### 목표 아키텍처
```
[현재 — 로컬 개발]
  로컬 PC
  ├── 운영통계자료.xlsx → preprocess.py → processed.pkl
  ├── SQLite (work/dashboard.db)
  └── Streamlit → http://localhost:8501

[중간 단계 — 백엔드 구축 (진행 중)]
  사무실 PC
  ├── MariaDB (운영통계·거래처마스터·단가마스터·거래명세서이력[정규화] 테이블)
  ├── FastAPI (scripts/api.py, port 8000, 로그인 인증 포함) → MariaDB
  └── Streamlit → requests로 FastAPI 호출 (http://localhost:8501, 기존 화면 그대로 유지)

[최종 목표 — Next.js + Vercel]
  Vercel (Next.js 화면, GitHub 연동 자동배포)
        │  HTTPS (Cloudflare Tunnel 경유)
        ▼
  사무실 PC
  ├── FastAPI (로그인 인증) → MariaDB
  └── (전환 완료 탭은 Streamlit 제거, 미전환 탭만 병행 운영)
```

### SQLite → MariaDB 전환 대상 파일 (FastAPI 경유 구조)
| 파일 | 변경 내용 |
|---|---|
| `scripts/db_config.py` (신규) | DB 접속 정보 — host·user·password·db명 |
| `scripts/init_db_mariadb.py` (신규) | MariaDB 4개 테이블 생성 (거래명세서이력은 의뢰서번호 단위로 정규화) |

### 거래명세서이력 MariaDB 정규화 설계 (2026-07-19 확정)
> 기존 SQLite `거래명세서이력` 1개 테이블(업무의뢰서번호목록을 JSON-in-TEXT로 저장)을 아래 2개 테이블로 분리. `품목`은 실제 라인아이템(수량·단가)이 아니라 업무명 요약 텍스트이고, 공급가액·세액·합계는 항상 거래명세서(그룹) 단위 합계로 계산·저장되던 값이라 — 개별 의뢰서 단위 금액 배분은 새로 만들지 않고, 집계값은 그룹 테이블에 그대로 두고 "의뢰서번호 목록"만 정규화함.

| 테이블 | 역할 | 주요 컬럼 |
|---|---|---|
| `거래명세서` | 거래명세서번호 단위 집계·상태 (구 거래명세서이력의 그룹 정보) | 거래명세서번호(PK), 거래처명, 담당자, 발행일자, 품목(요약), 공급가액, 세액, 합계, 발송여부, 발송일, 파일경로, 등록일 |
| `거래명세서_의뢰서` | 거래명세서에 속한 업무의뢰서번호 (구 업무의뢰서번호목록 JSON 정규화) | id(PK), 거래명세서번호(FK), 업무의뢰서번호, UNIQUE(거래명세서번호, 업무의뢰서번호) |

- `scripts/init_db_mariadb.py` 구현 완료. `거래명세서_의뢰서.거래명세서번호`는 `거래명세서.거래명세서번호`를 참조하는 FK (ON DELETE CASCADE) — 거래명세서 삭제 시 소속 의뢰서 행도 함께 삭제됨
- 채번용 `거래명세서번호_카운터` 테이블은 기존 SQLite 구조 그대로 유지 (사업부·연월 단위 순번)
- **MariaDB 테이블 총 6개**(운영통계자료·거래처마스터·단가마스터·거래명세서·거래명세서_의뢰서·거래명세서번호_카운터) — plan 문서의 "4개 테이블" 표현은 이 설계 확정 전 초기 추정치였음

### 핵심 계산 로직 (출력 vs 봉입)

> **출력과 봉입은 별도 행이 아니라 같은 행에 함께 기록됩니다.**

| 지표 | 사용 컬럼 | 설명 |
|---|---|---|
| 출력량 (장비 기준) | `출력페이지` (장비출력페이지) | 장비가 처리한 페이지 수. 양면 뒷면 미인쇄도 포함 |
| 출력량 (실제 기준) | `청구페이지` (실제출력페이지) | 실제 인쇄된 페이지만 집계 |
| 종이 소비량 | `장수` (출력용지 장수) | 사용된 종이 장 수 |
| 봉입량 | `건수` (봉입건수) | 봉투에 넣은 건 수 |

**과금(거래명세서) 기준:**
- 거래처별로 다름: `출력페이지` 기준 또는 `청구페이지` 기준
- 카드사 등 대형 거래처는 `청구페이지`(실제출력페이지) 기준으로 거래명세서 발행

**업무의뢰서번호 단위 청구 계산 규칙:**
```
[경우 1] 첫 행만 청구페이지 > 0, 나머지 행은 모두 0
  Row 1: 청구페이지 = 500  ← 전체 합계가 이미 첫 행에 표기됨
  Row 2: 청구페이지 = 0
  Row 3: 청구페이지 = 0
  → 청구 = 500 (첫 행 값 그대로 사용)

[경우 2] 2번째 이후 행 중 청구페이지 > 0 인 행이 하나라도 존재
  Row 1: 청구페이지 = 200
  Row 2: 청구페이지 = 150
  Row 3: 청구페이지 = 0
  → 청구 = 200 + 150 + 0 = 350 (첫 행부터 마지막 행까지 합산)

[경우 3] 그룹 내 모든 행의 청구페이지 = 0
  Row 1: 청구페이지 = 0, 출력페이지 = 200
  Row 2: 청구페이지 = 0, 출력페이지 = 100
  → 청구 = 200 + 100 = 300 (전체 행의 출력페이지 합산)
```

| 재발송 | 반송된 우편물을 다시 발송하는 작업 |
| 재발행 | 분실·훼손 등으로 문서를 다시 발행하는 작업 |
| 업무의뢰서 | 거래처가 요청한 업무 단위 문서 |
| 작업내역서 | 실제 작업을 기록한 내부 문서. "거래처명 - 작업명" 형식 |

## 🔑 주요 결정사항

- **반제품 처리 (2026-06-07 확정):** 반제품여부=Y인 행은 봉입 작업이 없으므로 해당 행의 건수를 0으로 처리. preprocess.py `apply_반제품_logic()`에서 청구페이지 계산 전에 자동 적용.
- **출력/봉입 집계 방법:** 출력과 봉입은 같은 행에 함께 기록됨. `건수`=봉입건수, `출력페이지`=장비출력페이지, `청구페이지`=실제출력페이지로 각각 집계
- **청구 단위:** `업무의뢰서번호` 기준으로 청구페이지를 계산. 단, 거래명세서 발행 시 여러 업무의뢰서번호를 합쳐서 1장으로 발행하는 경우도 있음
- **청구페이지 계산 규칙 (업무의뢰서번호 그룹 기준):**
  - 경우 1 — 첫 행만 청구페이지 > 0, 나머지 모두 0 : 첫 행의 청구페이지 그대로 사용 (전체 합계가 이미 표기된 것)
  - 경우 2 — 2번째 이후 행 중 청구페이지 > 0 존재 : 첫 행부터 마지막 행까지 청구페이지 합산
  - 경우 3 — 그룹 내 모든 행 청구페이지 = 0 : 전체 행의 출력페이지 합산으로 청구
- **과금 기준:** 거래처별로 다름. 카드사 등 대형사는 `청구페이지` 기준으로 거래명세서 발행
- **공급가액 계산 공식 (확정):**
  ```
  봉입건수    = 업무의뢰서번호 그룹 내 전체 건수 합계
  추가용지    = 장수_합 - 봉입건수_합  (장수 또는 봉입건수가 0이면 0)
  출력료      = 확정청구페이지 × 출력단가
  봉입료      = 봉입건수 합계  × 봉입단가
  추가봉입비  = (삽지_사용량_합 + 추가용지) × 추가봉입단가
  용지제작비  = 용지_사용량_합 × 용지제작단가
  봉투제작비  = 봉투_사용량_합 × 봉투제작단가
  삽지제작비  = 삽지_사용량_합 × 삽지제작단가
  공급가액    = 출력료 + 봉입료 + 추가봉입비 + 용지제작비 + 봉투제작비 + 삽지제작비
  세액        = 공급가액 × 10%
  합계        = 공급가액 + 세액
  ```
  - 추가용지 = 봉투 없이 용지만 투입된 수량 (장수 - 봉입건수)
  - 단가 필드가 DB에서 null인 경우 0으로 처리 (NaN 연산 버그 방지)
  - 모든 단가는 거래처·업무명·작업명 조합별로 상이 → 단가마스터 fallback 조회
  - (업무의뢰서번호, 작업명) 단위로 단가 각각 적용 후 합산 (2026-06-21 완료)
- **거래명세서 Excel 품명(D열) 작성 로직 (`generate_거래명세서_excel()`, `scripts/app.py:741` 이후):**
  - 선택된 의뢰서번호들을 `(작업명, 거래처명, 업무명)` 기준으로 그룹핑 → 그룹(=작업명)마다 6개 고정 품목을 계산
    ```
    품목순서(정렬 기준) = 출력비 → 봉입비 → 출력자재비 → 봉입자재비 → 추가봉입비 → 삽지비
    A열 코드            = 출력비:P, 봉입비:M, 출력자재비:F, 봉입자재비:E, 추가봉입비:M, 삽지비:M
    ```
  - 품목별 수량 × 단가:
    ```
    출력비     = 청구페이지 × 출력단가
    봉입비     = (봉입건수 + 각대대봉투수량) × 봉입단가
    출력자재비 = 용지수량 × 용지제작단가
    봉입자재비 = (일반봉투수량 + 각대대봉투수량) × 봉투제작단가
    추가봉입비 = (삽지수량 + 추가용지) × 추가봉입단가
    삽지비     = 삽지수량 × 삽지제작단가
    ```
  - **단가가 0이거나 수량이 0이면 그 품목 행 자체를 만들지 않음** → 무상 자재(예: BC카드 봉투 무상 제공)는 거래명세서에 해당 항목이 아예 표시되지 않음 (위 "유상/무상 자재 제공 방식" 규칙과 연동)
  - **행을 합치는 기준은 `(품목, 작업명, 단가)` 조합** — 여러 의뢰서번호가 같은 작업명을 공유하면 수량·금액이 한 행으로 합산되고, 작업명이 다르면 같은 품목이라도 별도 행으로 분리됨
  - **최종 품명(D열) 표시 형식:** `f"{품목}({작업명})"` — 예: `출력비(개인일반)`, `봉입비(기업예외)`. 작업명 값이 비어있으면 품목명만 표시
  - **정렬 순서:** 품목순서(출력비→봉입비→출력자재비→봉입자재비→추가봉입비→삽지비)가 1순위, 같은 품목 내에서는 작업명 문자열 순
  - B열(발행 구분날짜, `MM월DD일` 형식)은 첫 번째 행에만 표시되고 나머지 행은 비움. I/J/K열은 각각 수량·단가·금액
  - **품목 행 개수 제한 → 2026-07-17부터 사실상 무제한 (아래 "거래명세서 Excel 템플릿 — 가변 품목 행" 항목 참고)**
