# 플랜: 거래명세서 "고객사별 청구 규칙" 엔진 + 미리보기 편집 기능

## Context (왜 필요한가)

미발행 목록에서 "거래명세서 요청"을 누르면 자동 계산된 품목표를 그대로 보여주는 읽기 전용 미리보기만 있는데, 고객사마다 실제 제출 양식이 달라 자동 계산 결과(코드 P/M/E/F 단위로 잘게 쪼개진 항목)를 그대로 못 씁니다. 처음엔 "미리보기 화면에서 그때그때 수동 편집"으로 계획했으나, 사용자가 원하는 건 **한 번 규칙을 정의해두면 같은 거래처+업무명의 다음 명세서부터 자동으로 그 규칙대로 고객사 양식이 만들어지는 재사용 가능한 규칙 엔진**입니다.

**사용자 확정 사항(2026-07-22):**
- 화면 구성: **왼쪽 = 시스템 자동계산 원본 표(코드/품목/작업명/수량/단가/금액)**, **오른쪽 = 규칙을 적용해 만들어지는 "고객사 청구 명세서"**
- 오른쪽 특정 행의 품명 셀을 클릭하면 **조건식 편집창**이 뜸(AND/OR 그룹으로 "공정 코드 == P" 같은 조건을 조합) — 결과 행의 수량·금액은 그 조건에 맞는 왼쪽 행들을 합산
- 조건식은 **거래처+업무명 조합별로 저장** — 같은 업무명이라도 거래처마다 다른 규칙을 가질 수 있음, 다음에 그 거래처+업무명이 다시 선택되면 저장된 규칙이 자동 적용됨
- 규칙으로 만들어진 오른쪽 표도 **수량보정·새 행 직접 추가** 등 추가 수정이 가능해야 함(수동 편집 기능은 규칙 위에 얹는 보조 기능)
- 편집은 발행 전(미리보기 단계)에만, 확정하면 고정 / 화면·Excel 둘 다 반영 / 원본도 이력으로 남음 / 병합 시 단가가 다르면 "—" / 편집된 거래명세서는 부분취소 불가, 전체취소만 가능
- 조건식은 **품목명·작업명 텍스트 "포함함(contains)"** 비교도 지원(코드는 "일치함"만)
- 코드표 `추가봉입비`를 `"M"`에서 **`"MM"`으로 변경**해 봉입비(M)와 구분
- **전체 합산(코드 구분 없음) 규칙**도 지원 — 조건 그룹을 하나도 안 넣으면 "전체 매칭"으로 취급

## 개념 정리 — "규칙"과 "이 건의 최종 내용"은 다른 것

- **청구품목규칙** (재사용, 거래처+업무명에 저장): "어떤 조건의 원본 행들을 묶어서 어떤 이름의 결과 행을 만들지"에 대한 **구조적 정의**. 확정할 때마다 자동 저장/갱신되어 다음 명세서부터 재사용됨
- **거래명세서_품목** (이번 건 전용, 거래명세서번호에 저장): 규칙 적용 결과에 사람이 수량을 더 보정하는 등 **이번 한 건에서만 있었던 손질까지 반영된 최종 확정 내용** + 원본 스냅샷(이력용). 수량보정 같은 1회성 손질은 규칙에는 반영되지 않고 이 건에만 남음
- 구분 기준: **"조건식 편집창을 통해 만든 행 = 규칙"**, **"그 행의 수량 칸을 직접 숫자로 고친 것 = 이번 건만 적용"**

## DB 스키마 변경 (`scripts/init_db_mariadb.py`)

### 신규: `청구품목규칙` (재사용 규칙, 거래처+업무명별)
```sql
CREATE TABLE 청구품목규칙 (
    id              INT AUTO_INCREMENT PRIMARY KEY,
    거래처명        VARCHAR(100) NOT NULL,
    업무명          VARCHAR(200) NOT NULL,
    순서            INT NOT NULL,
    최종청구품명    VARCHAR(200) NOT NULL,
    조건            JSON NOT NULL,     -- {"or":[{"and":[{"field":"코드","op":"==","value":"P"}]}, ...]}
    등록일          DATETIME DEFAULT CURRENT_TIMESTAMP,
    수정일          DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_규칙 (거래처명, 업무명, 순서)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```
조건 필드는 MVP로 **코드·품목·작업명 3개**. 연산자는 **일치함(==)**과 **포함함(contains)** — 코드는 일치함만, 품목·작업명(텍스트)은 둘 다 선택 가능.
`조건["or"]`가 빈 리스트면 **전체 매칭**(코드 구분 없는 합산 규칙).

### 신규: `거래명세서_품목` (이번 건 전용 최종 내용 + 원본 이력)
```sql
CREATE TABLE 거래명세서_품목 (
    id              INT AUTO_INCREMENT PRIMARY KEY,
    거래명세서번호  VARCHAR(30) NOT NULL,
    구분            ENUM('원본','최종') NOT NULL,
    순서            INT NOT NULL,
    코드            VARCHAR(10),
    품목            VARCHAR(100),
    작업명          VARCHAR(200),
    수량            DECIMAL(12,2),
    단가            DECIMAL(12,2),
    금액            DECIMAL(14,2),
    FOREIGN KEY (거래명세서번호) REFERENCES 거래명세서(거래명세서번호)
        ON UPDATE CASCADE ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### `거래명세서` 테이블에 컬럼 추가
```sql
ALTER TABLE 거래명세서 ADD COLUMN 편집여부 TINYINT DEFAULT 0 AFTER 발송여부;
```
편집된(자동계산과 다른) 거래명세서는 부분취소를 막고 전체취소만 허용하기 위한 플래그.

## 백엔드 변경

### 1. `scripts/billing.py`
- **코드표 변경**: `코드맵`의 `"추가봉입비": "M"` → `"추가봉입비": "MM"`(109-111행). `코드표순서`(113행)에 `"MM"`을 `"M"` 바로 뒤에 추가: `["P", "M", "MM", "E", "F", "H", "BB", "AB", "D"]`
- `build_품목행()`은 그대로 유지(왼쪽 "원본" 표의 소스). 반환하는 정렬행에 **코드**를 명시적으로 포함하도록 보강
- 신규 `평가_조건(row, 조건)`: 원본 행 하나가 저장된 조건(JSON, OR-of-AND 트리)에 맞는지 True/False 판정. `op`가 `"=="`이면 완전 일치, `"contains"`이면 `조건값 in 대상텍스트`. `조건["or"]`가 빈 리스트면 무조건 True
- 신규 `적용_규칙(정렬행, 규칙목록)`: 각 규칙의 조건에 맞는 원본 행들을 모아 수량·금액 합산 + 단가는 매칭된 행들이 전부 같으면 그 값, 다르면 None("—") → 결과 행 리스트 반환. 미분류(어느 규칙에도 안 걸린) 원본 행은 별도 반환. **원본 행은 순서가 빠른 규칙부터 검사해 처음 매칭되는 규칙 한 곳에만 속함**(이중 청구 방지)
- Excel 작성부(현재 `generate_거래명세서_excel()`의 zipfile/XML 조작부, 181행~)를 `write_거래명세서_excel(정렬행, 총합계, 거래처명, 업무명, 발행일)`로 분리 — 기존 `generate_거래명세서_excel(df_all,...)`은 이 함수에 위임(Streamlit 경로는 완전히 그대로 유지)

### 2. `scripts/api.py` — 신규/변경 엔드포인트
- `GET /청구품목규칙?거래처명=X&업무명=Y` — 저장된 규칙 목록 조회(없으면 빈 배열)
- `PUT /청구품목규칙` — 그 거래처+업무명의 규칙 전체를 통째로 교체(DELETE 후 INSERT)
- `POST /거래명세서미리보기` 응답 확장: 기존 `품목`(왼쪽, 코드 필드 추가) 유지 + `청구품목규칙` 조회 → `적용_규칙()` 실행 → `규칙적용결과`(오른쪽 초안), `미분류` 추가
- `POST /거래명세서요청` 확장: `품목_최종` 필드 추가, 서버 재계산 "원본"과 비교해 다르면 `편집여부=1`, `거래명세서_품목`에 원본·최종 저장, `규칙` 필드는 `PUT /청구품목규칙`과 동일 로직으로 함께 저장
- `GET /거래명세서엑셀/{no}` — `거래명세서_품목`(구분='최종')을 그대로 읽어 `write_거래명세서_excel()`에 전달(재계산 안 함)
- `POST /거래명세서부분취소` — `편집여부=1`이면 400으로 차단

## 검증 방법
1. `python -m py_compile scripts/billing.py scripts/api.py`
2. `python scripts/init_db_mariadb.py` 재실행(로컬+사무실 PC) — 신규 테이블 생성 확인
3. `평가_조건`·`적용_규칙` 단위 테스트(실제 품목행 예시로 AND/OR 조합 여러 케이스)
4. 리팩터링 회귀 확인(SKILL-20) — `write_거래명세서_excel()` 분리 전후 기존 발행 건 Excel 바이트 동일한지 대조
5. 실제 흐름: 미리보기 → 조건 규칙 2개 정의(예: P끼리, M끼리) → 확정 → 같은 거래처+업무명으로 새 의뢰서 미리보기 다시 열어서 저장된 규칙이 자동 적용되는지 확인 → 수량보정 → 확정 후 규칙은 안 바뀌고 이번 건 최종값만 반영됐는지 DB로 확인 → Excel 다운로드해서 내용 일치 확인 → 테스트 데이터 정리
6. `npx tsc --noEmit`·`npx eslint .`, Playwright 브라우저 종단 확인

## 비개발자용 확인 체크리스트
1. 미발행 목록에서 특정 거래처 의뢰서 선택 → "거래명세서 요청" → 미리보기 좌/우 화면이 뜨는지 확인
2. 오른쪽 표의 품명 칸 클릭 → 조건 편집창이 뜨는지, "공정 코드 = P" 같은 조건을 넣고 저장하면 그 조건에 맞는 왼쪽 항목들의 수량·금액이 합쳐져서 오른쪽에 나오는지 확인
3. 확정 → 같은 거래처의 다른 의뢰서로 다시 "거래명세서 요청" → 방금 만든 규칙이 자동으로 적용돼서 오른쪽 표가 바로 채워지는지 확인
4. 오른쪽 표의 수량 하나를 직접 고쳐서 확정 → 다운로드한 Excel에 고친 값이 그대로 들어있는지 확인
5. 조건 그룹을 하나도 안 넣고 최종청구품명만 입력(전체 합산 규칙)해서 저장 → 왼쪽의 모든 항목(코드 구분 없이)이 하나의 결과 행으로 합쳐지는지 확인
