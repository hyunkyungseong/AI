> 상세: `docs/CHANGELOG.md` 2026-08-14 항목("수정이력 3건 보완", "8/13~14 감사이력·수정이력 관련 기능 전체 — 사무실 PC 배포 완료") 참고.

## Context (왜 하는가)
어제(2026-08-13) 만든 감사이력(`거래명세서_수정이력`) 기능을 실사용하면서 사용자가 3가지 문제를
발견했습니다.
1. "새 행 추가"로 빈 행(수량·단가·금액이 전부 0)만 만들어도 실제로 아무 값도 안 채웠는데
   "품목추가(이전값 —, 이후값 0)" 이력과 "편집됨" 배지가 생김.
2. 발행요청목록/발행완료에서 거래명세서를 취소하면 그 거래명세서에 쌓여있던 수정이력 로그까지
   함께 사라짐 — 감사이력의 목적(누가 뭘 했는지 계속 남기기)에 맞지 않음.
3. 취소·되돌리기 자체도 "무엇을 왜 취소했는지" 수정이력에 남기고 싶음.

## 조사로 확인한 사실 (실제 코드 직접 확인 완료, 재조사 불필요)

### 1. 0값 새 행 오탐
`_품목_변경_이력()`(`scripts/api.py` 1562행 부근)은 최종목록에만 있고 기준목록엔 없는 항목을
무조건 "품목추가"로 기록합니다. "새 행 추가" 직후 값을 안 채운 행(수량=0·단가=0·금액=0)도 여기
걸립니다. `billing.적용_규칙()` 결과를 거를 때 이미 쓰던 것과 같은 필터(`수량!=0 or 금액!=0`)를
여기도 적용하면 됩니다.

### 2. 취소 시 로그 소실 — 원인은 FK CASCADE
`거래명세서_수정이력`은 `거래명세서번호`에 `ON DELETE CASCADE` FK가 걸려 있습니다
(`scripts/init_db_mariadb.py`). `거래명세서부분취소()`의 전체취소 분기(`DELETE FROM 거래명세서 ...`)가
실행되면 이 CASCADE로 그 거래명세서번호의 수정이력 행도 통째로 삭제됩니다. `거래명세서_품목`
(원본/최종 스냅샷)에도 동일한 CASCADE FK가 있어 같이 사라지는데, 이건 그대로 둬도 되지만(스냅샷은
원래 "이 거래명세서가 존재하는 동안"의 상세 자료), 수정이력만은 살아남아야 합니다.

**두 곳에서 추가로 처리 필요**:
- `GET /거래명세서수정이력`(전체 조회, "수정이력" 탭)은 `거래명세서_수정이력`과 `거래명세서`를
  INNER JOIN해서 거래처명·담당자를 가져옵니다(`scripts/api.py` `발행목록()` 근처) — 거래명세서가
  삭제되면 INNER JOIN 때문에 그 행 자체가 조회 결과에서 사라집니다(DB에 남아있어도 화면에 안 보임).
- `GET /거래명세서품목이력/{no}`(개별 "편집됨" 팝업)은 거래명세서 헤더가 없으면 404를 던져서
  ("수정이력" 탭에서 취소된 건을 클릭해도) 수정이력 자체를 볼 방법이 없습니다.

### 3. 취소·되돌리기 흐름 확인
- **발행요청목록("취소" 버튼, mode="대기")**: `Tab4IssuedList.tsx`의 `handleCancelClick()` →
  `executeCancel()` → `POST /api/invoice-cancel` → `POST /거래명세서부분취소`(전체 의뢰서
  선택이면 거래명세서 DELETE, 일부만이면 UPDATE). 레벨1·레벨2 둘 다 이 경로.
- **발행완료("발행 취소(되돌리기)" 버튼, mode="완료")**: `handleStatusChangeClick("unpublish")` →
  `publishOrUnpublish()` → `POST /api/invoice-unpublish` → `POST /거래명세서발행취소`(발송여부만
  0으로 되돌림, 의뢰서 연결·거래명세서 행은 그대로 유지). **사용자 확인: 새 버튼을 만들지 않고
  이 기존 버튼에 사유 입력만 추가하기로 확정.**
- 두 액션 모두 공용 `ConfirmDialog.tsx`를 씁니다(현재는 사유 입력 UI 없음).
- **사용자 확정**: 발행요청목록 취소는 사유 선택(안 써도 진행), 발행완료 "발행 취소(되돌리기)"는
  사유 필수.

## 설계 (구현 시 그대로 따를 것)

### DB 스키마 (`scripts/init_db_mariadb.py`)
`거래명세서_수정이력`:
- FK(`ON DELETE CASCADE`) 제거 — `거래명세서품명이력`과 동일하게 "거래명세서가 지워져도 남는
  독립 이력" 성격으로 전환. 마이그레이션은 `information_schema.TABLE_CONSTRAINTS`로 실제 제약
  이름을 조회해 `ALTER TABLE ... DROP FOREIGN KEY`로 제거(하드코딩된 `_ibfk_1` 등은 환경마다
  다를 수 있어 안전하게 조회).
- `거래처명 VARCHAR(100)`, `업무명 VARCHAR(300)` 컬럼 신규 추가(등록 시점 값을 그대로 저장 —
  거래명세서가 나중에 지워져도 "어느 거래처·업무였는지"가 로그 자체에 남도록 비정규화). 신규
  설치용 `CREATE TABLE`도 동일하게 반영.
- 인덱스 `INDEX idx_거래명세서번호 (거래명세서번호)` 신규 추가(FK 제거로 자동 인덱스도 없어지므로
  조회 성능 유지용으로 명시).

### 백엔드 — 감사이력 기록 시 거래처명·업무명 채우기
- `거래명세서요청()`: 기존 INSERT들(공급가액/세액/품목목록)에 `거래처명=요청.거래처명,
  업무명=요청.품목`(이미 "업무명 여러 개를 쉼표로 합친 문자열"로 쓰이고 있는 필드, 재사용) 추가.
- `_품목_변경_이력()` 호출부의 INSERT도 동일하게 두 컬럼 추가.

### 백엔드 — 0값 새 행 필터 (`_품목_변경_이력()`)
"품목추가" 분기 진입 직후, 최종행의 수량·금액이 둘 다 0이면 이력을 만들지 않고 건너뜀(값이 전혀
없는 빈 행은 "실제 추가"로 보지 않음) — `billing.적용_규칙()` 결과 필터와 동일한 기준 재사용.

### 백엔드 — 취소·되돌리기 로그 기록
- `거래명세서부분취소_요청`에 `취소사유: Optional[str] = None` 추가. `거래명세서부분취소()`에
  `사용자: str = Depends(auth.get_current_user)` 추가(2026-08-13 `거래명세서요청()`에서 이미
  쓴 패턴 그대로). 사전 검증 SELECT에 `거래처명, 품목`도 함께 가져와서(이미 그 값 알고 있음,
  재조회 불필요), DELETE/UPDATE 직전에
  `INSERT INTO 거래명세서_수정이력 (거래명세서번호, 거래처명, 업무명, 필드명, 비고, 수정자)
  VALUES (..., '취소', f"{전체취소 or 부분취소}(의뢰서 {n}건){' — ' + 사유 if 사유 else ''}", 사용자)`.
- 신규 `거래명세서발행취소_요청` 모델(`거래명세서번호: str`, `취소사유: str`, 필수). 서버에서
  `.strip()` 후 빈 값이면 400으로 거부(프론트 검증과 별개로 서버가 최종 방어선, 이 프로젝트 기존
  관례). `거래명세서발행취소()`에 `사용자: str = Depends(...)` 추가, UPDATE 전 거래처명·품목을
  SELECT해 `필드명='발행취소(되돌리기)', 비고=요청.취소사유`로 INSERT.

### 백엔드 — 삭제된 거래명세서도 이력 조회 가능하게
- `GET /거래명세서수정이력`(전체 조회): `거래명세서_수정이력`을 `거래명세서`와 하던 INNER JOIN을
  LEFT JOIN으로 변경 + `거래처명`·`업무명`은 이제 `h.거래처명`·`h.업무명`(비정규화 컬럼)에서
  바로 읽음(담당자만 LEFT JOIN으로 살아있으면 표시, 취소된 건은 빈 값).
- `GET /거래명세서품목이력/{no}`(개별 팝업): 거래명세서 헤더가 없어도 바로 404 내지 않고, 먼저
  `거래명세서_수정이력`에 그 번호로 행이 있는지 확인 — 있으면 `{"존재함": false, "편집여부": false,
  "세액": 0, "원본": [], "최종": [], "수정이력": [...]}`로 응답(둘 다 없을 때만 진짜 404).

### 프론트엔드
- **`ConfirmDialog.tsx`**: 옵션 prop `reasonRequired?: boolean`, `reason`, `onReasonChange` 추가
  — 주어지면 메시지 아래 `<textarea>` 렌더링, `reasonRequired`면 빈 값일 때 확인 버튼 비활성화.
- **`Tab4IssuedList.tsx`**: `reason` 상태 추가. "취소"(`kind:"cancel"`) 다이얼로그는
  `reasonRequired=false`, "발행 취소(되돌리기)"(`kind:"unpublish"`)는 `reasonRequired=true`로
  분기해 `ConfirmDialog`에 전달. `executeCancel()`은 payload에 `취소사유: reason || undefined`,
  `publishOrUnpublish()`는 kind==="unpublish"일 때만 payload에 `취소사유: reason` 추가. 다이얼로그
  열 때마다 `reason` 초기화.
- **`InvoiceHistoryDialog.tsx`**: 응답에 `존재함===false`이면 원본/최종 비교 그리드 대신 "이
  거래명세서는 취소되어 품목 비교는 볼 수 없지만, 수정 이력은 아래에 남아있습니다" 안내 문구 표시
  (수정이력 표는 그대로 렌더).
- **`Tab4EditHistory.tsx`("수정이력" 탭)**: 응답 타입에 `업무명` 추가, 표에 컬럼 추가, 기존 검색어
  필터(`거래명세서번호·거래처명·수정자`)에 `업무명`도 포함(별도 필터 UI 없이 같은 검색창 재사용).

- `python -m py_compile scripts/api.py`, `npx tsc --noEmit`·`npx eslint .`·`npm run build`

  2. 총계 override로 거래명세서 생성 → 전체취소(DELETE) → `GET /거래명세서수정이력`에 그 이력이

  4. 발행요청목록에서 사유 없이 취소 → 성공 + 수정이력에 "취소(의뢰서 N건)" 행 기록
  5. 발행완료에서 "발행 취소(되돌리기)" 시도 — 사유 안 쓰면 확인 버튼이 비활성화되는지, 사유
     입력 후엔 정상 처리되고 수정이력에 "발행취소(되돌리기)" + 사유가 기록되는지
  6. "수정이력" 탭 검색창에 업무명 일부를 입력 — 해당 행만 필터링되는지
