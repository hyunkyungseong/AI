# 버그 수정: 미발행목록·발행요청목록 "예상공급가액"이 "부가세 포함" 거래처에서 부가세만큼 부풀려 표시됨

> 상태: ✅ 완료 — 코드 수정·검증·사무실 PC 배포·GitHub 커밋/푸시(`e87494d`)까지 전부 완료(2026-08-23).
> 봉입비 중복청구 수정(`bug_봉입비_수작업중복청구.md`) 검증 도중 사용자가 같은 거래명세서
> (D-202608-00093, 현대해상 자동차증권)에서 발견한 별개의 버그.

## Context — 왜 필요한가

사용자가 거래명세서 D-202608-00093(현대해상, 19개 의뢰서)을 미리보기에서 조건식 수정 없이 그대로
확정했는데, 발행요청목록의 "예상공급가액"(18,537,330원)과 "청구공급가액"(16,852,782원)이
1,684,548원이나 차이 났음 — "편집 안 하면 두 값이 일치해야 한다"는 기존 이해와 어긋남.

## 원인

- `calc_공급가맵()`(미발행목록·발행목록의 "예상공급가액" 계산에 사용)이 반환하는 "합계"는 단가마스터
  단가를 그대로 곱해 더한 **부가세 미반영 원시값**이다.
- 이 거래처+업무명(현대해상 자동차증권)은 `부가세구분='포함'`(단가 자체에 부가세가 이미 녹아있음)로
  등록돼 있음 — 이 경우 원시값은 사실상 "부가세가 이미 포함된 총액"과 같은 크기가 되는데(단가에
  부가세가 녹아있으므로), 실제 확정·저장 로직(`build_품목행()` → `billing.부가세_표시분리()`)은
  이 원시값을 **역산해서 공급가액·부가세로 정확히 분리**해 저장한다(2026-08-12 도입).
- `scripts/api.py`의 `/미발행목록`·`/발행목록`(`GET`)이 이 역산 분리 과정 없이 `round(가격["합계"])`를
  그대로 "예상공급가액"으로 써버려서, "포함" 거래처에서는 부가세만큼(≈총액의 1/11) 부풀려 보였다.
  "별도"(부가세 별도 계산) 거래처는 애초에 원시 합계=공급가액이라 이 버그의 영향이 없었음(그래서
  지금까지 발견이 안 됐던 것으로 추정).

## 수정

`scripts/api.py`에 헬퍼 `_예상공급가액_표시(가격)` 신규 추가 — `billing.결정_부가세구분()`으로
부가세구분을 판정한 뒤(작업명별로 섞여 있으면 예상치 단계이므로 발급을 막지 않고 "별도"로 예상,
기존 `/예상공급가액` 엔드포인트와 동일한 관례) `billing.부가세_표시분리()`로 확정 저장 로직과 동일한
방식으로 표시값을 계산한다. `/미발행목록`·`/발행목록` 두 곳의 `예상공급가액 = round(가격["합계"])`를
이 헬�러 호출로 교체(2곳, 각 1줄).

레거시 `/예상공급가액`(프론트엔드 미사용 확인됨) 엔드포인트는 이미 자체적으로 `부가세_계산()`을
거치고 있어 이번 버그의 영향 대상이 아니었음(수정 안 함).

## 참고 — 영향 범위가 예상보다 컸음

처음엔 이번에 고친 3개 거래처+업무명(봉입비 자재단가 등록분)만의 문제로 보였으나, 실제로는
**"부가세구분=포함"으로 등록된 모든 거래처**(BC카드 9개 업무명, 교보생명보험 6개, 삼성화재해상보험
11개, 현대해상 3개 등)에서 "예상공급가액"이 부가세만큼(총액의 약 9~10%) 부풀려 표시되고 있던,
훨씬 넓은 범위의 기존 버그였다(2026-08-12 부가세 표시분리 도입 이후 계속 존재 — 오늘 처음 발견).
"청구공급가액"(확정 저장값)은 처음부터 정확했으므로 실제 청구·발급된 금액 자체에는 영향 없음 —
미발행·발행요청 단계의 "예상" 표시 화면에만 국한된 문제였음.

## 후속 개선 — 라이브 재계산 대신 저장된 "기준" 스냅샷 재사용 ✅ 완료 (2026-08-23, 같은 날)

665원 잔여차 원인을 설명하자 사용자가 "미리보기 편집창에서 저장된 조건식으로 계산된 공급가액을
저장해뒀다가 그대로 쓰면 안 되냐"고 제안 — 실제로 가능함을 확인:

- `거래명세서_품목`에는 2026-08-18부터 구분='기준'(조건식 적용 후·사람이 손대기 전 스냅샷)이 이미
  저장되고 있었음(감사이력 기준선 용도로 도입).
- 이 스냅샷 합계에 `부가세_표시분리()`만 적용하면 실제 확정 저장값과 **완전히 정확히 일치**(D-202608-00093:
  665원 → 0원, D-202608-00088도 0원)함을 확인.
- 애초에 `/발행목록`이 "조건식 적용 결과를 라이브로 반영"하려면(대안으로 검토했던 방식) 미발행
  3,301건 규모에서 20초가 걸려(실측) 성능상 불가능했는데, **이미 저장된 값을 읽기만 하면 되므로
  이 문제 자체가 없어짐** — 정확도와 성능을 동시에 얻은 更 나은 해법.

**구현**: `scripts/api.py`의 `GET /발행목록`에 `거래명세서_품목(구분='기준')` 합계 조회 추가,
`billing.부가세_표시분리()`로 표시값 계산 — 거래명세서번호 단위로 계산해 그 거래명세서에 속한
의뢰서 라인 전부에 동일하게 붙인다(기존 "확정공급가액"과 동일한 패턴). 기준 스냅샷이 없는(2026-08-18
이전 확정된) 거래명세서는 기존 `calc_공급가맵()` 기반 계산으로 폴백(현재 DB엔 이 케이스 없음,
안전장치 목적). `/미발행목록`은 조건식 적용 결과 자체가 없어(요청 전) 변경하지 않음 — 오늘 이미
고친 부가세 반영 버전 그대로 유지.

**화면 표시 문구도 함께 정리(사용자 요청)**:
- `frontend/components/InvoiceSelectionTable.tsx` — 미발행목록 "예상공급가액" 헤더에 안내 툴팁
  추가("시스템 자동계산 값입니다 — 조건식 적용·확정 후 실제 청구 금액과 다를 수 있습니다")
- `frontend/components/InvoiceIssuedLevel1Table.tsx`(발행요청목록·발행완료 공유) — 헤더 라벨
  "예상공급가액"→"수정전공급가액", "청구공급가액"→"확정공급가액"으로 변경(내부 데이터 필드명은
  유지, 표시 텍스트만 변경)
