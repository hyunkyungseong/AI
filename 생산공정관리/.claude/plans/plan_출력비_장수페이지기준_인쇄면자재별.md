## Context — 왜 이 작업을 하는가

거래명세서에서 "출력비"(용지 인쇄 비용)를 계산할 때, 사람이 직접 확인한 "청구페이지" 값이 없으면
용지 자재사용량(실제 종이를 몇 장 썼는지)을 기준으로 출력비를 대신 계산합니다. 이때 "장 수"를
그대로 청구할지, 인쇄된 "페이지 수"(양면이면 한 장에 2쪽)로 환산해서 청구할지를 결정하는 값이
`단가마스터.인쇄면`(단면/양면)입니다.

지금 구조의 문제 두 가지가 사실 하나로 이어져 있습니다:

1. **`인쇄면`이 거래처+업무명(+작업명) 전체에 딱 하나**로만 설정되는데, 실제로는 같은 작업 안에서도
   자재(용지 종류)마다 단면/양면이 다를 수 있습니다(예: 내지는 양면, 표지는 단면). 지금 구조는 이걸
   표현할 방법이 없어, 자재가 섞인 작업에서 출력비가 실제와 다르게 계산됩니다(96315 사례로 발견,
   `bug_인쇄면_자재별관리.md`).
2. 반대로 어떤 거래처는 애초에 "페이지 수"가 아니라 "장 수" 자체를 청구 기준으로 삼는데(계약 조건),
   지금 코드는 이 구분 자체가 없이 **항상 페이지 수 기준**(양면이면 무조건 ×2)으로만 계산합니다
   (`plan_장수기준_출력비청구_조사.md`).

사용자가 짚어준 통합 규칙(2026-08-22 확정): **단면 용지는 장 수 = 페이지 수(같음)이고, 양면 용지는
"장 수 기준"이면 그대로, "페이지 수 기준"이면 ×2**. 즉 지금 하나로 뭉쳐 있던 "인쇄면"(자재의 물리적
속성)과 "청구단위"(거래처와의 계약 조건)를 서로 다른 축으로 분리하면 두 문제가 동시에 풀립니다.

## 확정된 설계 (AskUserQuestion으로 사용자 확인 완료, 2026-08-22)

- **인쇄면(단면/양면)** → 거래처 레벨에서 **자재(용지 종류) 레벨**로 내림. 자재별로 설정 안 하면
  기존처럼 거래처+업무명 레벨 값을 그대로 씀(회귀 없음).
- **청구단위(장수기준/페이지기준)** → 자재가 아니라 **거래처+업무명(+작업명) 단위**(계약 조건이므로,
  사용자 확정). 기본값 "페이지기준"(지금 동작과 동일 — 기존 거래처는 결과가 안 바뀜).
- 최종 배율: `장수기준` → 항상 ×1 / `페이지기준` → 단면 ×1, 양면 ×2.
- `청구페이지있음`(사람이 직접 확인한 값이 있는) 경우를 처리하는 `_자재비례배분_처리()`는 이미 확정된
  총량을 자재 비중으로만 나누는 함수라 이번 변경과 무관 — 손대지 않음.

## Phase 6 — 출력자재비(F)에도 인쇄면 확장(같은 날, 후속 요청) ✅ 완료

**계기**: 사용자가 화면 테스트 중 실제 발행된 삼성화재해상보험 청구서를 캡처해 제보 — "내지제작비"
(출력자재비/F, 5원)가 규격 "page"로 인쇄돼 있고 실제로 출력비(P)와 같은 페이지 수 기준으로 청구되고
있었음. 로컬 96315 데이터로 대조해보니 실제로는 F가 raw 장 수(62,692장)로만 계산되고 있어, 페이지
단가(5원/page)로 등록된 자재는 지금 코드로는 **절반만 청구**되는 구조적 결함이 있었음.

**설계 — 출력비(P)와 다르게, 거래처 레벨 인쇄면으로 자동 폴백하지 않음**: F는 원래 "실제 쓴 장 수"가
원칙(종이는 몇 장 썼는지로 재료비가 정해짐)이라, 지금까지 전 거래처가 예외 없이 장 단위로 청구돼
왔음. 여기에 거래처 레벨 인쇄면 폴백을 걸면, 이미 정상(장 단위)인 다른 거래처의 F 자재(예: 표지제작비)가
거래처 레벨 인쇄면이 우연히 '양면'이라는 이유만으로 조용히 2배 청구되는 회귀 위험이 있음. 그래서 F는
**그 자재에 인쇄면을 명시적으로 등록한 경우에만** 배율을 적용하고, 미등록이면(절대다수) 지금까지와
완전히 동일하게 항상 장 수 그대로 청구 — 자재단가 등록 자체가 없는 거래처는 이 분기를 아예 안 타
회귀가 원천적으로 없음.
